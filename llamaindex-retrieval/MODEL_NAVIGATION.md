# RWKV 自主检索架构方向（提案）

**状态：设计提案，未实现、未部署、无模型验证。** 适用于 `/admin/#/try` 交互链路的下一版本。验收只看用户实际收到的最终答案（见 `docs/CURRENT.md` 当前主线）。

## 基本约束

- 不使用 BM25、词项打分、关键词预筛或向量召回。找资料、读资料、判断缺口都由 RWKV 完成。
- 代码只做传输、切分、排序、去重、预算、解析和校验（`ARCHITECTURE_RULES.md` 第 1 条）。RWKV raw 不改写，校验只记录；需要修复时发起有独立 trace 的新调用（第 4、5 条）。
- 不写题型、实体或问法专用分支（第 2 条）。
- 保留用户 10-19 指定的骨架：上下文整理 → 并发阅读 → 三叉归并 → 按缺口补查 → 终答。

## 依据：现在丢分的位置

| 证据 | 结论 |
| --- | --- |
| 旧72题：70/72 原文池充分，但仍有 23 题终答失败；平均交给终答 19.68 份文档 | 主要瓶颈在终答输入：太多、太杂 |
| 9 道退步：原证据 0/9 → 精简后的充分原文 8/9 | 终答应看少量对题的原文 |
| 112 份叶摘要中 28 份丢失关系/限定/否定；归并把正确的 2K 改成 4096 | 只靠摘要往上传会丢事实 |
| 问题导向逐文档阅读 + 终答只读所选原文：42→47/72 | 目前唯一测得收益的路径 |
| 5000 个标题分 40 批选择，8 批 length，选中 74 份文件，上下文耗尽无答 | 平铺标题目录不能用于大库 |
| 10-19 补查：72 题首轮查缺全部返回空 | 补查要有明确的判定依据 |
| `interactive_funnel.py:199`：每条补查问题都重读整个材料池 | 成本翻倍，新叶与已归并节点混合 |

参考项目中可迁移、且不违反上述约束的做法：

- RWKV-SearchReader：先把问题拆成“对象 × 需要的信息项”，每个信息项单独标记已找到/缺失，补查只针对缺失项；抽取读原文，不读摘要。
- RWKV-Agent（同一个 7.2B G1K 模型的实测）：单次交给模型的页面控制在 4k token 以内，长页先按问题逐字摘句；多个来源放在同一个带标签的块里，而不是一条接一条（顺序给出时偏信最后一条，−15pp）；去掉 few-shot 示例；预填输出开头稳定格式。

## 新链路

```
① 上下文整理 + 信息项清单
② 分层导航选材（替代平铺标题目录）
③ 并发片段阅读（选片段 ID，不写自由摘要）
④ 三叉归并（向上传片段 ID + 程序携带的逐字原文）
⑤ 按信息项补查（只读新材料）
⑥ 终答（只看入选逐字原文 + 信息项状态）
```

### ① 上下文整理 + 信息项清单

在现有 `CONTEXT` 调用里多输出一项 `needs`：回答当前问题必须找到的信息项列表，由模型决定数量，不设上限。示例结构：`{"question": "...", "needs": [{"id": "I1", "text": "A 的发布时间"}, ...]}`。

`needs` 是之后阅读、归并、补查、终答共同使用的对齐依据。整理失败如实返回，不由程序补出清单。

### ② 分层导航选材（核心改动）

问题：只给标题，标题不包含的事实就找不到；平铺几千个标题，模型会多选、超出上下文。

做法：建库时预先生成导航卡片，查询时让模型逐层选择。

1. **建库阶段（离线，一次性）**：
   - 程序按结构切出 文档 → 章节 → 块 的树。可复用 `verbatim_chunking` 的标题路径。
   - RWKV 为每份文档、每个章节写一张短卡片（1–3 句内容概括 + 涉及的对象名），与原文哈希、提示词版本一起存储。
   - 卡片标记为“模型派生导航线索”，只用于选择，**不作为事实证据**，不进入终答。
   - 文档多时，按目录或主题把卡片再组成上层分组卡片（同样由 RWKV 写），形成三到四层树。
2. **查询阶段**：
   - 从顶层开始，每批把若干张卡片和问题、`needs` 一起交给 RWKV。模型对每张卡片给出 `high` / `maybe` / `none` 三档判断，不输出排序分数。
   - 程序只展开 `high` 和 `maybe` 的子节点，`high` 优先（这是允许的排序）。逐层下降，直到章节/块级。
   - 不限制选中数量。由阅读预算决定一次读多少：按 `high` → `maybe` 的顺序排队，预算用完后，剩余候选记为“未读”，留给补查轮。预算耗尽要如实记录，不悄悄丢弃。
   - 每次调用的输入都只有一批卡片，避免平铺几千标题的 length 失败。
3. **Web**：
   - 查询词由模型生成（沿用 `needs`）。
   - Tavily 全文快照按同样的结构切分。页面短的直接进入 ③。页面长的先建临时卡片，或按 RWKV-Agent 的做法逐字摘句压缩到 4k token 以内（单次 256 token；摘句必须逐字出现在原页面里，不满足就记录失败，改为按块阅读）。

### ③ 并发片段阅读

把现有 `LEAF` 自由摘要改为 `span_ids_v1` 风格（统一核心中已有实现，可复用合同）：

- 输入：问题、`needs`、一块原文。原文按 640/80 的片段带 ID。
- 输出：
  - 相关片段 ID 列表；
  - 每个片段对应的信息项 ID；
  - 一句简短说明（可空）。
- 程序校验 ID 属于本块，并把被选片段的**逐字原文**和来源一起登记，不经过模型转述。

这样关系、否定、表格条件留在原文里，不再依赖摘要能否保留下来。

### ④ 三叉归并

每个归并节点最多 3 个直接子节点（保持现状）。

- 输入：
  - 子节点的说明；
  - 子节点选中的片段（由程序附上逐字原文，并标明“原文”）；
  - `needs`。
- 输出：
  - 保留的片段 ID（必须是子节点片段的子集）；
  - 每个信息项的状态 `found` / `missing` / `conflict`，并附片段 ID；
  - 简短说明。
- 归并只做选择和对齐，不改写原文。trace 区分“实际原文输入”和“继承来源链”（第 3 条）。

所有来源放在同一个带标签的块里（编号、标题/URL、来源类型：知识库/官网/第三方），不逐条追加。

### ⑤ 按信息项补查

- 根节点上 `missing` 或 `conflict` 的信息项就是补查对象。补查由模型的判定结果驱动，不再单独问“还有没有缺口”。
- 新的一轮：针对这些信息项，先展开 ② 中“未读”的 `maybe` 候选，再让模型生成新查询（KB 导航 / Web）。
- **只读本轮新增的材料**，新叶与旧根一起再归并一次。这同时修复 `interactive_funnel.py:199` 的重读问题。
- 轮数和时间按资源时限记录；信息项全部为 `found`，或模型判定无法继续核实时停止。

### ⑥ 终答

- 输入：问题、`needs` 及其状态、根节点保留的逐字片段（同一个带标签的块，按 token 计预算）、根节点说明。
- 不看未入选的候选，不看中间摘要（第 3 条）。
- 提示要求：回答每个信息项；`missing` 项明确说明未找到；正文用片段编号引用。
- 不放示例；预填 `<think></think` 后接输出开头。
- 引用无效或信息项没有被覆盖：只记录。需要修复时发起一次独立的新终答调用，旧 raw 保留（第 5 条）。

## 与现状的差异

| 环节 | 现状 | 新方向 |
| --- | --- | --- |
| 选材 | 平铺标题，每批 128 个 | 建库时生成的分层卡片，三档判断，逐层展开 |
| 阅读产出 | 自由摘要 | 片段 ID + 信息项对齐 + 程序携带的逐字原文 |
| 归并 | 摘要再摘要 | 选片段子集 + 信息项状态 |
| 补查触发 | 单独询问是否有缺口（实测全空） | 根节点的 missing/conflict 项 |
| 补查阅读 | 重读整个材料池 | 只读新增材料 |
| 终答输入 | 模型总结 | 入选的逐字原文 + 信息项状态 |

## 实施与验证顺序（每步一个变量，按最终答案验收）

1. **终答输入**：在现有试用链路上把终答输入从“根总结”改为“根总结 + 入选逐字原文”（叶仍是摘要，用 `source_ids` 回溯原文块）。成本最低，与 8/9 和 47/72 的证据一致。
2. **片段阅读替代自由摘要**（③④），引入 `needs`（①）。
3. **补查改为信息项驱动、只读新材料**（⑤）。
4. **分层导航选材**（②）：先离线生成卡片并单独记录导航命中情况（只作诊断，不替代最终答案验收），再接入链路。
5. **Web 长页逐字摘句**。

各步都在固定题集上记录最终答案的正确/错误/缺失/退步，非盲测须注明；已见题不进入训练。导航卡片、片段选择是后续 StateTune 的天然训练目标，训练数据另取未进入评测的来源族。
