# 2.9B Reader 后续诊断与本机 state 验证

当前尚未改善完整 RAG 的答案质量。五组 Reader 候选都未通过，不改生产默认协议。本轮完成了并发对照、输入消融、已核验权重的本机复现和 state 梯度通路验证。完整 RAG 成绩仍是先前的 **8 题 / 29 项必要事实：0 正确、25 遗漏、4 错误**，不能用本页诊断调用数代替新增题目或准确率。

## 固定 Reader 输入

从已公开的 CAN FD、多开发文档两题 trace 中固定 **16 个真实来源：8 个正例、8 个负例**。正例确有可回答信息，负例只含标题、主题、外链或错误对象；标签绑定原文位置与 SHA。每个来源均只有一个 E 单元，因此这组检查不能验证多单元定位能力，也不是盲测或完整检索重跑。

所有实验保留完整原问题、历史、原文、父标题及原始输出。候选只改变各自声明的输入变量，未重新检索。除开放思考前缀实验外，均使用 complete 闭合前缀；每项最多 1,024 输出 tokens，零 state，EOS 配置 `[0]`。外部自然终止原因仍未核验。

| 候选 | 候选模型调用 | 格式通过 | 8 个正例召回 | 8 个负例中的合法误选 | 严格来源成功 / 16 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 每次只呈现一个原子问题 | 80 | 78/80 | 0/8 | 0/8 | 7/16 |
| 再明确本次只判断该子问题 | 80 | 76/80 | 0/8 | 0/8 | 6/16 |
| 仅精简来源和父上下文追踪元数据 | 16 | 14/16 | 0/8 | 0/8 | 6/16 |
| 允许 Reader 思考 | 16 | 4/16 | 0/8 | 0/8 | 3/16 |
| 添加三个通用虚构格式示例 | 16 | 13/16 | 0/8 | 4/8 | 3/16 |

严格来源成功要求同一来源的所有调用均符合协议，且选择并集等于标签。格式失败不算正确拒选，合法误选为零也不等于没有负例失败。拆分任务会增加模型调用，不增加来源数；没有把总读取来源预算变成每个子问题各读一遍数据库。

五组均保留相邻控制。原始 joint 控制通常格式为 15/16、严格来源为 7/16，正例召回始终 0/8；各组精确成绩、差异和原始字节见对应 `review/REPORT.md`。开放思考的 11 项未闭合结果保留失败；示例候选的 4 次非空选择全部是负例误选，没有把输出增多当成质量改善。

## 并发与复现

两组原始 batch8 各做 batch → 八次单条调用 → 原 batch 重复，共 20 次 HTTP、48 项输出。16 个槽位在这三种执行中逐字相同，其中一个槽位是 Planner。这个小样本没有观察到批处理损害输出，不是 32 并发吞吐或所有输入质量的证明。

独立重复的两个 80 项控制有完全相同的 10 个 HTTP 请求正文、成员和顺序，却出现 6 项 raw 输出变化。另两次恢复历史请求完整字节的重放，也未恢复 CAN 的历史输出。已排除“仅 JSON key 顺序变化足以解释历史漂移”的说法，尚未确定漂移原因，未据此声称服务更换了权重。

七组已完成外部生成实验共 **480 项输出 / 74 次生成 HTTP**。后面的 state 上传探针只额外完成 **2 项输出 / 1 次生成 HTTP**；上传尝试另计一次，未收到响应。合计为 **482 项外部输出、75 次生成 HTTP、1 次结果未知的上传尝试**，没有重计跨报告引用的控制记录。

## 可核验的本机 2.9B

官方文件为 [固定版本 G1j 2.9B](https://huggingface.co/BlinkDL/rwkv7-g1/blob/53b2ec91e3c68c90fe1ae9b878fc4ce0b15d69f0/rwkv7-g1j-2.9b-20260831-ctx16384.pth)，5,896,273,469 bytes，SHA256 `966f3420f833532aae3fb1fd6326533b08d43d23b7b03eaa2f0694a30b64a239`。下载和全部基础权重 key/shape/finite 检查通过；远端同名模型的实际 SHA 仍未核验。

- 本机 RTX 5070 Ti 加载了全部 1,062 个基础张量、2,948,065,280 参数。40-token BF16/FLA 前向与一次 backward 后，32 层初始 WKV state 梯度全部有限且非零，全部基础权重保持冻结且无梯度。
- 此次 peak allocated 为 6,218,369,024 bytes，约 5.79 GiB，含首次编译的前后向分别约 33.67/46.25 秒。它不代表 8K/16K 训练的显存或暖机吞吐。没有优化器更新、正式训练或收敛成绩。
- 用冻结的 `rwkv` 0.8.30 纯 Torch 路径重放 WinJS、CAN 两个原始正例输入，各为 780/952 个本地 tokens，均生成 `NONE` 后遇到实际 EOS0。本机能复现这两条漏选，但不能由此推出两端权重和实现完全相同。
- 同一 40-token 通用输入的两种本地实现比较：零 state logits 相对 L2 为约 0.006211、top1 相同 39/40；固定非对称 state 为约 0.012088、40/40。零 state 的一个小 margin 位置改变了 argmax，不宣称逐 logit 等价，也不把短探针外推到长文。

PEFT 源码在本地保留用户原有修改的完整独立快照，原仓库未改动。公开包排除本轮未执行的旧 20B tokenizer 和历史 13.3B 启动脚本，精确路径、SHA、恢复来源和排除原因见 `ARCHIVE-SOURCE-EXCLUSIONS.json`；本轮执行所需模块及其 pin 保留。这是研究运行时，不是 RAG 生产代码。canonical state 文件轴为 `[H,V,K]`，训练和推理边界转换均有来源记录。

## 外部 state 尚未验收

`external-zero-state-v1` 先完成两条零状态控制，然后尝试上传本机生成的全零、未训练 state。上传约 10.5 MB 后出现 `ReadError`，没有 HTTP 响应或 `state_id`；远端是否创建状态未知，因此无法定位或删除可能创建的文件。没有重试，没有执行带 state 的生成、后控制或删除。

这次只验证了上传前控制，不能声称 state 上传/加载已经跑通。即使全零 state 对照成功，也只说明兼容性，不能证明非零 state 的效果或完整动态记忆恢复。

资源安排为本机优先；资源不足时允许 `rwkv-8222` GPU2，仍使用 2.9B。本轮没有访问或启用该服务器。后续需完成训练与推理长序列对齐、独立训练/留出数据和实际 tuned state 验证，再比较证据召回、负例误选、完整事实和引用支持。
