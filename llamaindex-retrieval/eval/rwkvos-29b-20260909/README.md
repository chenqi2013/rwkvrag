# 外部 RWKV G1j 2.9B 基线与长输入实验

本轮将完整 RAG 迁至外部 batch 推理和本机 OpenSearch。服务自报模型为 `rwkv7-g1j-2.9b-20260831-ctx16384`；所有质量实验省略 state_id，没有 statetune。使用原本已公开的开发题，不是盲测。最新源码含传输、可选完整输入计数与中断统计修复；旧实验始终绑定各自冻结源码，不以新代码回写结果。

事实项分数与整篇答案合格不同：全部可见断言和引用都要审阅。候选即使填对更多必要事实，新增错误来源、无依据断言或恢复已撤回要求仍不晋级。模型生成的 sources/evidence 字段不是实际输入证据。

固定材料每轮 8 模型调用、1 次共享 batch HTTP。默认 stop 与 EOS 两轮有 7 个回答逐字一致，另一个仅有用词差异，错误仍在。省略前缀末尾 > 只影响输入，模型实际返回的 > 保留在 raw，正文范围通过 Unicode answer_span 标记。

Wiki 使用 5,000 文档 / 45,960 原文块，索引 `rwkvrag-bm250820-wiki-5000-20260908`，本机 UUID `lYXmlfpMRPCJ5tyq9YW67g`。本机恢复后全部块 ID、原文及上下文与旧冻结 scroll 对齐，物理索引 UUID 是新的。条件为每查询 80 候选、按查询轮转、总读取 80 来源、4 题并发、最多 32 模型项并发、batch8、规划/读取各输出 1024、Writer 2048；约 27.1 秒完成这一轮。该数字不是吞吐或稳定性基准。

## Trace 中的故障位置

Wiki 共 170 模型调用 / 28 个共享 batch HTTP：8 Planner、160 Reader、2 Writer。

- 6 个 Planner 格式失败：4 个 Markdown JSON 围栏、2 个顶层对象数组；部分长历史还超过查询条数。原 parser 没有修复这些输出。
- 进入读取的两题，8 项必要事实全部位于真正送入 Reader 的原文或父级上下文，未因候选或来源预算丢失。
- 160 个 Reader 返回 146 个纯 NONE、14 个格式错误，0 个合法非空选择。CAN FD 的关键调用输出答案值/改写正文而不是编号；开发文档的关键调用全部 NONE。
- 两个 Writer 输入来源均为空：一题拒答，仍遗漏所需事实；另一题生成四个错误值。无证据时没有用代码替模型生成拒答。

因此本轮不能把零证据归因为 BM25 没找到材料，也不能将问题简化成读取来源不够。规划范围、协议遵从、正负证据识别和 Writer 事实引用需要分开改进。

补充两项 Planner-only 对照各 8 调用 / 2 个 batch HTTP，沿用相同模型、完整历史、采样与输出预算：单一子问题列表格式通过 4/8（基线 2/8），但存在范围退化；仅将原操作要求放在完整任务之后为 0/8，还恢复旧对象和撤回字段。两项均未晋级，未接着跑端到端来混淆变量。

## 超长输入

三个相同合成事实处于前、中、后位置，分别加入 45 / 84 / 167 篇完整 Wiki 干扰文章。每档一次，3 次计数加 3 次生成，均 200，无重试；没有执行检索。

| 实际服务输入 tokens | 正确事实 | 正式支持 | 人可读支持 | 完整通过 | 往返 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 8,169 | 3/3 | 3/3 | 3/3 | 是 | 3.23 秒 |
| 16,375 | 0/3 | 0/3 | 0/3 | 否 | 4.35 秒 |
| 32,624 | 1/3 | 0/3 | 1/3 | 否 | 4.63 秒 |

8K 有三处引号内标点/连接词改写，另记逐字引文差异。冻结主协议要求语义支持，不能事后新增逐字门槛替换主分。若按逐字引文另算，完整为 0/3，作为附加敏感性单列。长度、干扰数量和位置距离共同变化，不能归因单一位置效应或外推普遍上下文上限。

离线参考词表与服务计数差 1–2 token，位置仅为参考坐标。32K 返回证明该请求未被 16K 拒绝门挡住，不能独立证明部署内部没有裁剪。所有 provider stop 仍为终止未核验；没有用输出重编码伪造真实生成 usage。

机制、SearchReader 对照与下一步结构见 [超长上下文说明](../../../docs/long-context.md)，接口与初始 WKV state / 完整会话 state 的区别见 [接口合同](../../../docs/rwkvos-api.md)。

## 新增工程验证

可选 `/tokens/count` 按每项最终完整 prompt 计数，原始收据和 prompt SHA 绑定；显式应用输入上限超限时不发该项生成，也不截断。默认关闭，保持旧基线条件。计数不等于事实保持或真实输出 usage。

HTTP 汇总按 batch_id/count_id 分别去重：已尝试、确认未尝试和未知分别记录。仅有 started 收据不能被算成已发送；有未知项时总次数为 null。默认关闭计数的真实旧基线全部有完成收据，原 HTTP 数字保持可复核。

真实计数检查已通过：同一完整 Writer prompt 服务计数 840，正常生成成功；设应用上限 1 后明确 budget_exceeded；此前 32,624-token 输入设上限 8,192 后也被阻止生成。共 3 次计数、1 次生成，精确 prompt 与字节 SHA 全部核验，没有把该工程检查另算质量提升。

全量 Python 回归 **590 通过 / 114 失败**，失败 ID 与纯净基点完全相同、没有新增失败；前端 19 项测试和构建通过，修改文件 Ruff 通过。初次误用不存在的 npm test 脚本在执行测试前失败，原始日志保留，随后用项目真实 node --test 入口完成验证。软件回归和新增真实计数检查见归档内 `publication-checks/` 与 `input-count-validation-v1/`。纯净基点的 114 项失败单列比较，不表示全量测试通过。前端将外部回答标为返回且终止/语义未核验。

## 原始记录

`ARCHIVE-SELECTION.json` 列出每个入选文件的路径、字节数和 SHA；`archives/RECORDS-MANIFEST.json` 绑定各压缩包。校验器先拒绝不安全成员，再核验全部解压字节。原始材料、负例、调用失败、未晋级候选、源码快照、逐断言审阅和索引恢复核查一并保留。

在 `llamaindex-retrieval` 目录运行下列离线校验；需要展开时另加 `--extract /新的空目录`：

```bash
python3 eval/rwkvos-29b-20260909/build_archive.py verify --manifest eval/rwkvos-29b-20260909/archives/RECORDS-MANIFEST.json
```

校验器只证明归档字节完整，不自动证明语义评分。冻结脚本中的原绝对路径保留当时环境，换机器重放需要显式映射；模型权重、运行时与认证不打包。上游源码按 pins 固定版本复取后另验 SHA。

归档省略可重新下载的 OpenSearch 运行时、下载包、运行数据和重复的 126MB 索引 scroll。逐字原索引已在 [第一轮 index 归档](../bm250820-rebuild-20260908/README.md)，本轮保存新索引恢复及逐条一致性证据。API 上游保存固定 commit、文件 SHA 和精确链接，原文件按清单复取；不重复打包上游源码缓存或 .git。

所有认证值均未入库。旧服务器的本任务服务与自动启动已停用；此轮只使用本机 CPU 和外部 API，没有本机训练。历史 13.3B 结果保留在 [原报告](../bm250820-followup-20260908/README.md)，不改写为 2.9B 分数。
