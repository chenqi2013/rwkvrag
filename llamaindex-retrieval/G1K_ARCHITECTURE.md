# RWKV G1K：任务与检索提示分离的架构候选

**状态：应用实现与离线合同测试完成；默认关闭，未通过真实 G1K 语义验收。** 不是把模型名换成 G1K 就自动启用，也不代表已训练或部署。遵守[架构规则](ARCHITECTURE_RULES.md)。

## 为什么调整数据流

不能假设 G1K 能靠复杂多层提示、长历史或更大的上下文自行纠正上游遗漏。任务解析、检索规划、证据选择和最终回答是不同职责：检索问句即使语法正确，也可能省略条件或引入额外属性。旧流程会把 Planner 输出的 queries 同时用作 Reader 任务与 Writer 字段提示。

候选把**当前任务**与**检索提示**分开，避免应用把后者当成用户要求。它修正的是输入边界，不证明模型会遵守边界，也不证明这是既有错误的唯一原因。

```text
原对话输入 ── 有历史：所选协议/任务解析模型 ── 当前问题 + 原始调用记录
原始问题   ── 无历史：逐字传递    ──┘
                                 │
                          TaskAnchor（应用数据）
                                 │
                   Planner：仅规划事实检索问句
                                 │
                   BM25 / 已配置检索服务与排序
                                 │
          Reader：当前任务 + 单份原文单元 + 检索提示
                    仅生成 {"answer":"YES"/"NO"}
                                 │
                 逐字原文、来源ID、坐标/hash绑定
                                 │
             Writer：当前任务 + 已选证据，输出原始正文
                                 │
                  引用/传输/预算审计，不改答案
```

固定材料接口跳过 Planner/检索/Reader，使用调用方提供的材料，仍保留任务解析与相同 Writer 合同。无历史不新增任务解析调用。

原对话在应用中保留，**实际送给解析模型的范围仍由历史协议决定**：旧G1K-v1只传上一用户消息，v2虽传完整角色历史但尚未通过语义验收。本候选不隐式切换历史协议；锚定错误的改写仍然是错误，不能因有hash就称有效任务已正确提取。

## 实现边界

- `task_contract.py` 的不可变 `TaskAnchor` 保存流水线入口问题或模型解析问题、独立任务JSON和原输入hash。历史解析结果绑定其call ID；`semantic_verified`始终为false。入口之前已有的API字段校验/空白规范化不由本合同改变。
- Planner 的 `fact_queries_v1` 提示与原始输出不变。queries 用于搜索与 Reader 查找提示，不再作为 Writer 字段列表。原计划、字段镜像和失败记录仍保留。
- Reader 新版本 `binary-task-v1` 同时收到当前任务与检索提示；每次仍读一个逐字单元并输出一个二元选择，不引入多字段语义Schema。旧 `binary-query-v1` 提示/解析不变。新提示保留原格式示例，并明确区分“有证据”与“答案为是/条件满足”；这仍是**待验证的模型行为**，代码不会据否定词等强制保留。
- Writer沿用 `evidence_first` 原提示，字段参数改为单元素的当前问题，与固定材料接口一致。不再注入Planner派生的字段列表；不删除整个字段参数，不补引用、改答案或生成程序拒答。
- 检索查询数、排序、按query的候选配额、原问题保留开关、Reader单元/查询调用组合均保持原配置。此候选没有宣称减少模型调用或提高吞吐；Reader增加完整任务输入，实际token与延迟可能增加。
- `task_contract` trace记录当前问题/任务/原输入hash、来源及改写call ID。Reader、Planner和Writer的绑定在请求内显式传递，不存入共享客户端可变状态；并发请求不共享任务内容。

## 为什么不把 RWKV State 当知识库

G1K是权重/模型代际，`g1j_plain`是历史命名的传输模板，两者不是同一个概念。本候选沿用已有单user消息、闭合no-think、EOS/解码及精确token校验，不凭名称猜测模板能力。[G1K连接设置](README.md#g1k-72b-native-连接配置)中的25600是具体服务的配置，不是所有G1K模型的通用保证，更不是可用原文长度。

RWKV recurrent State不是可寻址的逐字文档目录。训练初始State与读完某段前缀后的动态State也不同。当前设计：

- 原文、完整历史、任务与来源绑定留在应用数据层；Writer证据不被模型摘要替换。
- 各调用重新读取自己的输入；不自动续接前一请求，不合并不同文档的State，不假定固定尺寸State能无损记住任意长度历史。
- 可配置 `current_question / plan / reader / writer` 独立初始引用，见[State接口](NATIVE_STATE_ROUTING.md)。不创建/上传State，不复用旧G1J或其他大小模型的训练产物。
- no-ref不证明零State；有ref不证明实际消费或数值兼容。前缀缓存、分支State、训练—服务一致性和并发演化副本仍需独立验收，本候选没有实现它们。

## 显式配置与兼容性

新增设置（环境变量带`RWKVRAG_`前缀）：

| 设置 | 默认 | 候选 |
|---|---|---|
| `NATIVE_TASK_CONTRACT` | `legacy` | `anchored_v1` |

`anchored_v1`仅接受以下**已显式配置**的组合，不会替用户补齐或修改参数：

- `RAG_PIPELINE=rwkv`，native传输、`g1j_plain`，模型身份检查开启，三个传输阶段采用闭合no-think前缀。
- 非raw历史协议、非task-matrix。选择既有历史协议不等于该协议语义合格；尤其不能据此认定`current-question-v2`已经可用。
- Planner=`fact_queries_v1`，Reader=`binary_query`、individual、任务来源queries。global/per_query候选配额均可。
- Writer=`single`＋`evidence_first`，`native_writer_budget_policy=disabled`。暂不兼容funnel、matrix、整源packing；完整输入＋输出上限检查和请求级预算仍可用。
- 空证据策略必须为`fail`，引用审计策略必须为`fail_citation`，不让此候选重新启用已知危险的空材料写作/静默引用失败。这些门禁不判断语义、不改原文。
- State路由可完全关闭；一旦配置，必须显式声明`current_question`，不允许任务解析隐式借用plan。

仅显式设置`RWKVRAG_NATIVE_TASK_CONTRACT=anchored_v1`才进入候选。默认legacy保持旧请求和提示；原有配置不自动迁移。不因为模型ID含`g1k`就打开特性，也不因设置此项就认定端点权重属于G1K，实际模型必须另外绑定/验证。

## 激活前仍需验证

离线测试只验证数据流、字节、引用身份、失败边界和并发请求隔离，不验证模型选择/回答正确。实际验证应分开进行：

1. 固定材料Writer：原字段列表对照当前问题字段，保留普通题、否定、部分、缺失、冲突及引用失败。
2. 固定单元Reader：仅比较旧query-only与任务锚定合同，报告误选、漏选、非法输出和输入token变化。新Reader提示不只是添加一个JSON字段，任何收益不能未经消融归因于单个措辞。
3. 单独验任务解析的完整历史/条件保留，再看组合；不能把人工独立问题的分数当自动链路分数。
4. 各组件通过后才考虑真实检索/E2E和受控部署。训练需要独立数据/复核、来源隔离、token/mask/EOS/最长序列及数值/梯度验收，不由本设置放行。

本候选不预设G1K只能训练，也不把复杂Schema、宽松相关性选择或增加预算当成已验证的修复。
