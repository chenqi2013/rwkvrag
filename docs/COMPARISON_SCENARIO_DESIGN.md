# 面向实际检索的比较与选择场景

日期：2026-09-21。状态：场景设计草案；尚未采集新语料、建立金标、冻结新实验或运行模型。

## 为什么要调整

用户指出当前展示的比较题过于简单。上一轮188条主要用于复现基础错误与模型大小对照，不能代表实际检索体验。它保留180个不同prompt，但其中存在相同任务模板的换名换数；题目条数不等于真实场景覆盖。

这些题继续作为基础回归，不删除、不改写、不降低旧题门槛。新增场景单独报告，不与旧题混成一个高低难度不明的准确率。简单题仍会失败是实际缺陷，但只围绕这些题优化也不足以指导产品架构。

## 真实任务应覆盖的困难

| 困难 | 场景要求 | 需要检查的体验 |
| --- | --- | --- |
| 分散证据 | 多个候选的事实分布在说明书、部署文档、变更记录和表格中 | 系统自行找到两侧对应证据；不能只比较最先检索到的候选 |
| 条件和例外 | 默认配置、额外组件、授权级别、特定模式的能力不同 | 区分开箱能力与满足前提后才可用的能力 |
| 比较口径 | 不同硬件、并发、精度、任务或测试日期的结果 | 识别不可直接横比的测量，不从一个数字强行排名 |
| 时间和版本 | 同名产品多个版本、过期配置、明确修订及未解决冲突 | 解释结论适用版本；不能仅按抓取时间或“更新”字样选来源 |
| 多目标选择 | 多项硬约束、偏好优先级、代价和例外 | 先判断资格，再说明取舍；允许多个合理方案 |
| 证据不完备 | 部分候选缺参数、未说明、需要追加资料 | 说明已知范围，提出有针对性的补查或澄清，不把未知判成不支持 |
| 多轮变化 | 用户修改预算、部署规模、联网要求或撤回候选 | 更新受影响结论，仍保留未撤回条件与来源 |
| 知识库与网络 | 内部部署记录和外部版本文档存在差别 | 保留来源和版本边界；联网开关改变可访问证据，不悄悄补外部知识 |

材料长度和对象数量只是描述指标；不用堆入无关文字或换数字制造难度。每项困难必须来自任务所需证据及决策关系。

## 三个待落地的场景示例

以下是任务草案，不是已核实的产品事实，也没有预设赢家。

### A. 现有系统与替代方案的部署选择

问题：基于给定版本资料，对比现有RWKVRAG与WeKnora，判断哪个更适合某团队的内网文档场景。用户要求数据不能外发、可追溯引用、来源更新后可核查知识变化，并给定硬件和维护人员限制；需要区分现成能力、配置后可用、需要开发、没有证据四种情况。

资料应包含：两个系统指定提交的源码/配置、运行核验记录、产品说明、版本变更和已知限制。项目README声明不能替代部署实测；没有当前证据就不能填写“已支持”。输出可以是有条件推荐或缺口清单。

关键追问：用户允许仅联网获取公开资料，但内部文档仍不得外发时，哪些结论改变？保留来源访问与模型推理位置的区别。

### B. 推理模型与部署方式选择

问题：在给定硬件、并发、输入长度和响应时间要求下，比较不同模型/精度/部署方式，解释质量与资源取舍。材料混有不同测试条件、基座与State、首次请求与缓存后请求的记录。

资料应包含：冻结运行日志、模型身份、显存测量、调用参数、逐题答案与失败记录。不能把短输入并发1的数据直接推广到长输入多并发，也不能将“服务启动成功”当作容量达标。

关键追问：用户从短问答改为长文档比较后，原先推荐是否仍有依据？允许回答需要补测，并明确缺哪组可比测量。

### C. 故障方案比较与后续行动

问题：同一个检索质量问题存在“扩大检索”“改证据切分”“分层推理”“换模型”几种方案，根据一次事故的查询、命中文档、节点trace和版本变更，比较各方案能解决什么、不能解决什么，提出先后顺序和验证办法。

资料故意保留真实诊断的不确定性：某些阶段只知道执行完成，不知道语义正确；某些运行同时改变多个变量。正确输出应区分观察、推测和需要验证的因果关系，不要求凭有限记录猜出唯一根因。

关键追问：移除某条关键证据后，结论应收缩到哪里？新增相反记录后，应补查什么而不是反复罗列双方。

## 数据建设草案

首批建议24个独立场景：部署/能力、运行测量、版本迁移、故障决策各6个。数量为计划，不是已完成题库。候选数量通常3～6个，来源通常6～20份，但不设机械配额；两候选也可能有复杂且真实的条件差异。

- 每个场景保存自然问题、有效上下文、文档快照、版本/来源、可核查的期望事实与允许的结论范围。
- 优先来自现有项目真实使用任务及可授权的实际材料。公开材料用于实验前固定快照；尚未读过的项目/网页必须先核实，不能编造能力作为金标。
- 先完成8个不同场景的开发包，检查任务与证据是否合理；另16个场景在调参前按场景/文档来源隔离。未经过独立复核时明确标注，不称盲测。
- 每个场景可有条件变化、删除关键证据等派生追问；它们属于同一场景簇，不计成独立场景。训练、开发、留出按整个场景簇划分。
- 单独列真实材料与合成诊断材料。保留歧义及无法确定的结论；评分不用唯一措辞或关键词替代正确解释。

## 如何定位架构问题

同一场景分别记录三个层次，不混合计分：

1. **足量证据回答**：给定经核对的必要证据，检查事实、关系、取舍和收束。材料超预算时明确标记，不截掉关键例外后仍宣称完整材料对照。
2. **固定语料检索**：只提供问题及语料索引，让系统寻找和组织证据。检查遗漏哪项关键证据、在哪一阶段出错。
3. **交互体验**：在前端加入条件变更、引用核查、停止和补查；最后单独验证真实网络访问。网页快照回放不冒充实时联网。

以7.2B为主线。首次场景基线保持现有模型/State/提示/预算绑定；之后协议改造单独版本，不同时换模型、提示和检索配置。沿用[实验控制](EXPERIMENTS.md)，生成前冻结任务、材料、评分口径和执行绑定。

## 报告什么

- 用户能否据此行动：推荐有没有违反硬条件；是否说明取舍、适用范围和未决问题。
- 证据是否足够：关键候选/字段覆盖，断言有无正确来源，点击能否定位相应版本原文。
- 错误如何形成：证据未检出、字段/范围混淆、关系判断错误、总结失真分别记录。
- 是否及时结束：完成时间、首次有用内容时间、模型调用次数、token、持续复读、取消确认和未完成项。
- 不同有效结论按依据与约束评价；要求追问/补查的任务，不能以没有立刻选出赢家记失败。
- 旧基础题、普通问答与新增复杂场景各报分母与退步项。当前没有冻结新的数值晋级门槛，必须在运行前确定，不能看完输出再选。

## 与当前架构主线的关系

这些场景检验[原子→关系→候选小结→最终总结](LAYERED_REASONING_DESIGN.md)是否真正承接复杂需求：原子事实保留前提和版本；关系层允许不可比与未知；候选层保留全部硬条件；最终总结给出可用结论并准确说明边界。不会因为展示更复杂而推断该架构已实现或已有效。
