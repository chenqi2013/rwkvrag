# 大型GitHub比较：联网恢复后8题实测

## 结论

两新凭据basic与advanced分别单次验证均200；advanced共6结果、5份正文。随后以第一个凭据运行原8题，模型仍为7.2B零State及追加Writer指令候选。候选已经在固定材料退步，本次为真实链路诊断，不代表基线7.2B表现或正式部署质量。

8次全部保留：7次搜索成功、1次提供方异常触发熔断；5条回答达到2048 token上限，2条有答案但Planner失败，1条无答案。按预登记大型选型要求，实现者审读0通过/8失败，非独立盲测、非总体准确率。不能将HTTP 200或有搜索结果视为比较成功。

## 网络边界

单凭据、全实验应用串行、每次结束后至少6秒再搜索，未自动重试或切到第二个Key。搜索实际完成间隔由逐行日志保存；模拟测试验证两次并发进入仍间隔6.057秒，失败后下一次不发出请求。

最后一次异常仅保存RuntimeError，耗时约10.13秒，原bridge没有保留详细上游状态，因此不能确定是连接异常还是服务端错误。随后独立GET /usage返回200，仅证明该时点鉴权正常，不能恢复原失败请求的原因，也不能保证/search稳定。没有把补测覆盖原失败，更没有认定新账号已停用。

## 后续架构优先级

1. TaskSpec将对象、比较维度、有效硬条件与撤回要求分开；实际读取历史不等于把旧助手答案当证据。
2. Planner逐对象规划并标记缺口。不能以“解析失败后整题只搜一次”冒充覆盖全部项目。
3. Reader逐字绑定对象/字段/来源，验证页脚误选与材料截断；官方来源不足应明确记录，模型决定是否补查。
4. Relation逐维度检查双侧证据，再由Condition核对硬条件，最后Writer汇总；不把五项目原文直接堆给Writer负责全部关系推理。
5. 单独对照这些协议；保留原188普通/选择回归与本8题，不再用追加收束指令的失败候选作为优化结论。

以上为后续设计方向，未声称分层新链路或生产级限流已完成。
