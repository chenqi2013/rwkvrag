# 7.2B受控回放：重复性与旧State迁移

日期：2026-09-21。执行和评审：Codex实现者，非独立评审。用户授权继续验证后完成，**共1,890次新模型调用，0次训练更新，未晋级或部署正式问答**。

## 结论与架构影响

旧2K State不适合加载到所有ASSESS节点。它将大量事实问答压缩成“满足/不满足”，丢失数值、日期和对象；在缺少一侧证据时仍给出确定比较。零State同样有冲突处理、跨对象复制和幻觉问题，不能简单切回zero就认为已解决。

下一步应拆开事实提取、关系比较、硬条件判断和候选总结，并给每个节点明确的有效用户要求。当前实验没有执行这个新架构，不能把诊断结果当作新方案的收益。

### 具体体验问题

1. **事实值丢失**：复位9秒、开放日期2021年6月12日、连接上限7、代号Juniper等问题，zero给出具体值，训练组常只给“满足”。问周一几场时，训练组用“不满足”代替明确的0场。
2. **单侧比较被硬判**：只给甲的10/18小时、没有乙的值时，zero说明无法比较；训练组分别确定“不满足/满足”。证据ID合法仍不能保证比较成立。
3. **相同被说成冲突**：两款价格均290、容量均64GB，应是合格并列；训练组8个不同证据编号版本中7个称“证据冲突”，尽管最后也说无法唯一选择。
4. **上游丢失用户要求**：部分子问题只有“用户任务是什么/最新更正是什么”，判断输入里只有产品参数。zero有时从参数编出用户限制，训练组常套满足标签；这首先是任务信息传递问题。
5. **零State仍有严重错误**：白岭容量未记载时复制青川73L；将废止的青川999L草案归给白岭；把未记载的周三讲座数写成3场；把来源附注攻击当“用户最新更正”。本轮不能作为zero上线证明。

## 下一项实现重点

1. TaskSpec先保留有效用户对象、字段、阈值、否定和历史更正；每个模型节点接收它所依赖的要求片段，不能从产品值反推用户要求。
2. Fact节点输出实际值、单位、对象/模式、否定和逐字来源，禁止将通用事实协议设计成只有满足标签。先用7.2B zero State验证，旧2K不自动绑定。
3. Relation节点接收双侧同字段/范围的事实及来源；缺一侧由模型明确未知，结构审计拒绝缺侧却给确定关系。Condition节点才使用满足/不满足/未知/冲突。
4. 候选总结覆盖全部硬条件，偏好只在合格候选间比较；Writer保留这些结论与逐字来源，单独测试是否重新推荐已排除项及丢引用。

下一轮R2/R3须各自冻结提示、oracle输入范围和预算，分别测事实与关系，再测Writer承接。当前没有开始这些新协议模型实验，也没有新一轮训练。
