# 检索规划数据：标签先行试点

日期：2026-09-23。本试点沿用上一轮的12组备份主题新来源，但将教师工作拆为两次可追溯调用：先提出维度、条件、每对象搜索式，代码与预登记对象及 `grid/listed` 组合成完整规划；再让教师依据**不变的规划**写自然用户问题。每次原始请求、响应与局部失败留在本机忽略目录 `data/quality-runs/retrieval-state-plan-drafts-20260923/label-first-v1-00-12/`；[计数、原文哈希和 token 绑定](../../../artifacts/retrieval-state-data-20260923/LABEL-FIRST-PILOT.json)已保存。它是未复核草稿，**不是新训练集或检索质量验证**。

95条已用[编译器](../../../scripts/retrieval_statetune/prepare_plan.py)生成精确 batch 提示、只监督目标与 EOS 的 mask，字节哈希固定。[准入审计](../../../scripts/retrieval_statetune/audit_candidates.py)如预期拒绝：没有逐条独立复核，低于5000训练条与120训练来源族门槛，单族占比过高。原始教师输出与编译后的候选分开保存，没有将失败项改写为合格标签。

**结构改善不能替代来源与语义质量。** 抽看问题时，备份 topic 的6个仓库中混入通用脚本库 `alexanderepstein/Bash-Snippets`；某题据此比较其 PostgreSQL 版本兼容性与备份恢复冲突处理。这种题即使标签、字面覆盖和 token 全对，也不是自然的同类选型样本。其它 topic 也存在仅因 GitHub 标签相同、实际角色不同的项目。因而本轮没有扩大教师生成，更没有把95条送进 StateTune。当前120份采集快照可继续作为原始候选，但需另建**来源角色/可比性审读版本**，只从合适的项目组产生训练题；必要时补采新仓库，使训练分区达到120个可用来源族。

下一步按变量顺序：来源组审读和扩充 → 新盲集先冻结 → 将[规划协议](../../../llamaindex-retrieval/src/llamaindex_retrieval/retrieval_plan.py)接入默认关闭的实验检索路径，并区分待查格子与批次搜索预算 → 扩量生成、独立标签审读、准入审计 → GPU3 `fp32io16` StateTune 与同源快照成对评测。仅凭本试点不能推断真实网络检索已改善。
