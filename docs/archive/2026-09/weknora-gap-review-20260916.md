# WeKnora 对照评审：RWKVRAG 还差在哪里

> **历史记录，非当前状态。** 本文保留当时的实验、部署或设计结论；“当前”“最新”“下一步”均指原记录时点。当前事实与行动以[当前状态](../../CURRENT.md)为准。原路径：docs/weknora-gap-review-20260916.md。

评审日期：2026-09-16。

## 结论

WeKnora 值得借鉴，主要价值是把文档接入、问答、知识维护、人工修订与运行管理连接成产品闭环。RWKVRAG 已有 RWKV 原生问答、原文证据追踪和 StateTune 实验基础，但当前仍偏向研究与人工试用系统。

我们的首要任务是提高有据回答的稳定性，其次补齐知识更新和使用体验，再发展受约束的检索 Agent 与 Wiki。增加功能数量不能替代答案质量验收。

## 范围与证据边界

- WeKnora：读取官方 README、功能文档，并克隆 main，核对 Agent、Wiki 版本、数据源接口、任务认领和知识库权限等代码。固定提交为 `6f98ff80c3185679cc16f834faf42fc662770e68`。
- RWKVRAG：核对当前代码、架构规则、前端和已有评测材料；基准提交 `c9f72780cf6415ab53dd26c194c05c0566df2bde`。
- 本次为静态架构和产品差距评审，没有部署 WeKnora、重新运行模型评测或做两套系统的同条件性能比较。不能据此认定 WeKnora 的回答准确率、延迟或成本优于我们。
- “未发现”指本仓库所检查的实现，不代表外部网关或其他项目没有相关能力。历史验证记录也不代表当前服务的实际加载状态。

## 一、能力对照

| 方向 | WeKnora 的参考能力 | 我们当前状态 | 差距判断 |
| --- | --- | --- | --- |
| 文档接入 | 多格式解析、多数据源同步 | Markdown/MDX、文本 PDF、DOCX；另有 FineWiki Parquet 导入 | 基础上传已有；OCR、表格/演示文稿及外部同步不足 |
| 知识维护 | 目录树、片段编辑、历史版本与回滚 | 知识库/文件管理、片段浏览、文件重建索引 | 缺可修订且可追踪的内容维护流程 |
| 问答检索 | 快速 RAG 与独立 Agent 模式 | RWKV Planner → BM25 → Reader/Resolver → Writer | 默认原生链路尚无根据阅读结果继续检索的循环 |
| Wiki | 由来源文档生成页面，关联引用、链接和修订 | FineWiki 是导入的百科语料 | 尚无生成并持续维护 Wiki 的业务模型 |
| 使用体验 | 流式对话、阶段进度、引用交互 | 问答表单、多轮历史、来源列表、原始 trace 展示 | 已能试用；缺实时阶段进度、停止任务及完善的引用定位 |
| 后台任务 | 持久化操作、并发认领、失败队列及运行管理 | Mongo 记录任务、进程内 asyncio 并发、启动恢复 | 不能简单当作多实例可靠任务队列 |
| 权限 | 工作区角色和知识库级访问检查 | 所检查的应用路由未接入身份与资源授权 | 面向多人共享时需补齐；知识库 ID 不是权限边界 |
| 可观测性 | 运行追踪及队列管理 | 精确 prompt、原始输出、哈希、阶段耗时与调用收据 | 证据记录已有基础，缺聚合指标和运维视图 |
| 评测与发布 | 数据集驱动评测 API、多种检索指标 | 检索脚本、分阶段模型评测、独立语义复核 | 缺统一、可重复执行的发布验收流程 |

WeKnora 总体功能依据：[官方 README](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/README.md)。下文对关键差距给出更具体的实现依据。

## 二、最重要的差距及建议

### 1. 有据回答的可靠性：优先级最高

我们自己的 [2026-09-11 评测](../../../llamaindex-retrieval/eval/trace-eval-20260911/RESULTS.md) 已明确显示：

- Reader 的 60 道受控挑战由 48/60 提高到 60/60，但不能解释成完整 RAG 正确率。
- 固定 36 道通用 Writer 题，有据可用由零 state 的 10/36 提高到 Writer300 的 17/36，仍有明显不足。
- 完整 RAG 的 11 道新题，三份 state 组合事实完整为 11/11，但有据可用只有 8/11；差异来自引用未指向真正支持事实的片段。
- 完整 RAG 所测五档配置在 4 道复杂暴露题上均为 0/4 有据可用。这是小样本诊断，不能外推总体正确率。
- Planner150 单独组和组合组均出现 15/15 规划失败，实际回退到原问题；不能把结果解释为规划能力提升。

建议先建立固定验收集，分开检查：规划语义与格式、支持事实的片段召回、Reader 误选/漏选、Writer 完整性、引用支持、无证据处理、版本冲突、耗时和模型调用成本。特别加入“标题含答案关键词但正文不支持”的反例。

现有 [evaluate.py](../../../llamaindex-retrieval/src/llamaindex_retrieval/evaluate.py) 的 `recall_at_k` 实际按题统计预期标题是否命中，并不是逐证据片段的标准召回率。应保留其用途并明确命名，再补片段级标注与指标。

所有修复遵守 [架构规则](../../../llamaindex-retrieval/ARCHITECTURE_RULES.md)：由模型作语义决定；审计不修改原答案；需要重新生成时保留独立调用与 trace。

### 2. 文档更新必须可靠，不能只有“重新导入”

当前 [parsers.py](../../../llamaindex-retrieval/src/llamaindex_retrieval/parsers.py) 上传格式仅包括 `.md/.markdown/.mdx/.pdf/.docx`。扫描 PDF 无文字时直接要求先做 OCR；DOCX 将段落和表格分别收集再拼接，可能失去原来的交错顺序。复杂文档解析质量会直接影响后面的证据判断。

更具体的工程风险在 [tasks.py](../../../llamaindex-retrieval/src/llamaindex_retrieval/tasks.py) 的 `_run_file_job`：先删除该文件的旧索引，再建立新索引。如果新建失败，旧知识已不可完整检索。这里是代码路径推断，未做故障注入。

建议：

1. 原始文件不可变保存，解析结果、人工修订和索引版本分别记录。
2. 新版本索引完成并验证后切换查询可见版本；失败仍保留旧版可用。
3. 优先补真实业务需要的 OCR 和表格结构保留，并提供解析/片段预览。
4. 先实现一种数据源的增量同步，记录 external ID、版本/内容哈希、同步游标和删除标记。

WeKnora 的 [Connector 接口](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/internal/datasource/connector.go) 将校验、资源列表、全量、增量分开，并提供流式摄入与检查点恢复接口。这种接口划分值得借鉴；无需一开始接入所有平台，也不能把接口元数据里的名称都当成已实现的连接器。

### 3. 默认 RWKV 链路还不是可自主补证据的 Agent

[service.py](../../../llamaindex-retrieval/src/llamaindex_retrieval/service.py) 在 `rag_pipeline=rwkv` 时直接进入 [RWKVPipeline.ask](../../../llamaindex-retrieval/src/llamaindex_retrieval/rwkv_pipeline.py)。当前是一次规划、批量检索、阅读、作答；虽然支持多条查询、来源融合和多次 Reader 调用，但阅读后不会回到检索阶段。

仓库确实有 `active_retrieval.py` 和旧管线的多轮检索代码，不能因此认定默认原生链路已拥有这些能力。

WeKnora 的 [Agent 引擎](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/internal/agent/engine.go) 有显式执行循环、工具结果回填、迭代预算和取消处理。

建议先做受约束的检索 Agent：

- 初期只开放知识库搜索、读取原文和完成三个动作。
- 由 RWKV 判断缺少什么证据并提出下一次查询；代码只校验工具参数、执行检索和限制预算。
- 每轮记录新增证据、失败原因和停止原因，设置总调用、时间与上下文预算。
- 先固定一次补检索进行对照评测，确认复杂问题改善且简单问题没有明显退步，再扩大能力。

不应直接把 WeKnora 面向通用模型的长提示词和大量工具塞给 2.9B；当前 Planner 协议可靠性还需要先验证。

### 4. Wiki 的重点是知识维护机制

WeKnora 的 [Wiki 文档](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/website-docs/03-features/14-wiki.md) 和 [页面服务](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/internal/application/service/wiki_page.go) 表明，它不只是生成 Markdown：页面携带来源/片段引用，支持修改前快照、版本递增、回滚，以及问题报告和修复流程。

我们目前没有 Wiki 页面、页面修订、依赖关系或失效传播模型。FineWiki 的 5000 篇文章和 45960 个原文片段是测试语料规模，不能算作自动 Wiki 能力。

适合我们的最小设计是：

`不可变原文 → 可追溯片段 → 带证据的主题页草稿 → 审核发布 → 来源变更后标记过期并重建`

应保存页面版本、来源文档版本、片段 ID、生成调用 ID、人工编辑记录。生成 Wiki 属于派生内容，不能冒充原始证据；对事实的最终引用仍应能回读原文。先验证文档摘要页和主题页，再考虑图谱展示与自主修复。

### 5. 后台任务已有基础，但还缺多实例协作机制

[TaskManager](../../../llamaindex-retrieval/src/llamaindex_retrieval/tasks.py) 已有任务持久化、状态/进度、失败记录及重启恢复，不是纯内存任务系统。但执行由各进程 `asyncio.create_task` 和信号量管理；启动时读取可恢复任务再执行，所检查路径未见原子认领或租约。

由此推断，多进程同时启动时可能重复恢复同一个任务。进程内并发限制也不等于跨进程总量限制。

WeKnora 的 [任务仓储](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/internal/application/repository/task_queue.go) 提供原子批次认领、失败计数和死信记录，可参考其生命周期设计。

我们可以先在 Mongo 上实现原子认领、worker 标识、租约超时回收、幂等写入、有界重试和失败任务入口，不必立即引入整套新中间件。验收应包括处理时重启、双 worker 争抢、重试不重复写入和重建失败保留旧索引。

### 6. 面向团队使用前，补权限和用户反馈

当前 [api.py](../../../llamaindex-retrieval/src/llamaindex_retrieval/api.py)、[路由](../../../llamaindex-retrieval/src/llamaindex_retrieval/routers/admin.py) 和 [依赖注入](../../../llamaindex-retrieval/src/llamaindex_retrieval/dependencies.py) 未发现应用级身份与资源授权。外部网关是否保护当前部署，本次未核实。

WeKnora 的 [知识库访问控制](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/internal/middleware/kb_access.go) 会把文档/片段追溯到所属知识库，再实施访问控制。这比仅在界面隐藏按钮更值得借鉴。

我们应在多人共享前覆盖搜索、原文下载、片段、历史、trace 和管理操作的授权。对于当前单机研究阶段，此项不应挤占模型质量实验；对外提供服务时则是前置条件。

[SearchPage.tsx](../../../llamaindex-retrieval/web/src/pages/SearchPage.tsx) 已支持对话历史、来源和 trace，但等待 `api.ask` 完整返回。建议补阶段进度、停止操作、引用定位，以及“错答/漏答/引用错误”反馈。反馈绑定当次问题、输入来源和配置版本，经过独立审核再进入训练集。

### 7. 将已有评测资产变成日常发布流程

我们已有相当细的调用收据和独立语义复核，不应重新从零做评测。缺的是把这些能力合并成固定入口、长期结果记录和发布判断。

[历史验证记录](../../../artifacts/statetune-20260911/VALIDATION.json) 是 757 通过、114 失败、2 跳过；它说明历史失败集合未变化，不能代表全量测试通过。这份材料还记录当时未包含前端构建，而当前前端已恢复，因此也不能拿它作为当前整个产品的验收结果。

建议明确维护链路和旧回归测试的契约，逐项解释或修复历史失败；保持失败可见，不以批量跳过制造通过。统一运行固定材料、Reader、检索、完整 RAG 和前端检查，并将模型/state、prompt、索引、代码版本与结果绑定。

## 三、建议实施顺序与验收

以下为建议路线，本次没有改动业务实现或启动训练。

| 阶段 | 要交付什么 | 如何判断完成 |
| --- | --- | --- |
| P0：可靠问答 | 固定验收集；Planner 协议、证据选择、引用/无证据专项修复；清晰发布基线 | 留出题逐题有原文依据；报告事实、引用、拒答和耗时的独立指标；不以格式通过替代正确率 |
| P1：可靠知识维护 | 版本化文档与索引切换；解析预览；任务认领/恢复；基础反馈和阶段进度 | 重建失败仍可查旧版；重启和双 worker 不重复处理；错误能定位到阶段与版本 |
| P2：受约束 Agent | 知识库工具、有限补检索、显式停止与调用预算 | 同模型、同数据集比较单轮/补检索；同时报告质量增益和成本增量 |
| P3：Wiki 最小闭环 | 摘要/主题草稿、原文引用、人工编辑、版本回滚、来源变更标记 | 每页可追溯至原文版本；回滚可复核；源文档更新/删除后派生页不会静默维持有效状态 |
| 团队化前置 | 身份、知识库授权、历史/trace 隔离、操作审计 | 无权限用户不能通过搜索、下载、片段或历史接口访问受限知识 |

## 四、哪些经验应借鉴，哪些需要保持判断

**优先借鉴**：数据源接口与检查点、片段/页面版本管理、任务认领与恢复、清晰区分快速问答和 Agent、用户纠错入口。

**继续保留我们的方向**：RWKV 2.9B、BM25 无 embedding 基线、原始输出不可变、逐字证据与精确调用记录、分阶段 StateTune 对照。是否需要其他检索通道，应由同义改写和低词面重合题的召回实验决定，不能仅凭竞品使用向量检索下结论。

**不宜照搬的部分**：大量模型/存储适配、通用沙箱和渠道全集会增加维护成本；应由真实场景驱动。WeKnora 的 [评测文档](https://github.com/Tencent/WeKnora/blob/6f98ff80c3185679cc16f834faf42fc662770e68/website-docs/03-features/15-evaluation.md) 明确评估暂无独立 UI、结果存内存并在重启后丢失；BLEU/ROUGE 也不能替代事实与引用支持判断。对方有机制，不等于这些机制已经证明模型语义可靠。

最终建议：先把“可靠回答 + 可更新的证据库”做扎实，再将其扩展为“可补证据的 Agent + 可追溯维护的 Wiki”。
