# Tavily低频验证与请求放大诊断

2026-09-21。用户要求验证再次提供的10个Key，并检查是否代码请求过多。未修改生产配置、SearchReader源码或冻结实验。

## 实测

直接调用Tavily /search，绕过应用和Key轮换。10个Key各请求一次，并发1，每次完成后等待6秒，无重试。相同basic查询、最多1结果、不取正文。10/10均返回401，错误均为账号已停用，要求联系support@tavily.com。0个429，0个432/433。首个请求已经失败；本次低频测试无法恢复账号。没有换出口或尝试绕过限制。

这确认当前提供方报告账号停用，不能确认最初停用原因，更不能由401推断IP风控。是否因历史请求、账号关联或其他策略停用，需要服务商记录。此前8次成功的记录仍保留，不能改称从未可用。

## 代码问题与模拟复现

1. SearchReader search.py中的失效Key集合是进程内全局变量。rwkvrag web_retrieval.py每个查询启动一个新bridge进程，因此失效状态无法跨查询保留。
2. _post遇到401/402/403/429/432会立即切换下一个Key；429没有Retry-After/退避。健康锁只保护集合，不限制调用频率。
3. 应用默认同时运行2个搜索子进程，这不是每秒/分钟限流；多个应用实例也不共享此Semaphore。
4. bridge与应用把提供方详细错误压缩为泛化异常，前端难以分辨账号、限流、额度和网络故障。

使用8个假Key、模拟401、调用真实TavilyProvider逻辑：首次查询8次HTTP尝试，同进程第二次0次；模拟新进程重置全局后又是8次。全部为模拟，无真实网络调用。说明默认2查询、8失效Key时可能产生16次请求；大型实验8查询可能64次（忽略超时中断，不代表已观测历史请求数）。健康Key首次成功时立即返回，不会每次遍历全池。

## 结论与后续

请求放大缺陷已证实；它是风险因素，但没有证据证明它导致这次停用。修复应采用跨进程凭据健康状态、提供方统一限流与熔断、429有限退避、结构化脱敏错误；账号停用独立联系服务商确认。当前只完成诊断，未声称修复已部署。无需通过新增IP池猜测原因。
