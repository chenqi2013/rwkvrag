日期：2026-09-24（Asia/Shanghai）。用户要求**只准备数据，不训练**。本轮没有调用 RWKV 训练器、没有优化器更新、没有更换正式检索链路或模型。数据版本、教师原始响应和失败保持分开；旧 65 道联网题、434 道恢复知识库题、24 道固定材料题的题目与答案没有用于训练标签。

## 1. 来源从“topic 相同”改为角色审读

第一批 120 份 README 的 GitHub topic 混入通用脚本、示例应用等非同类项目；旧备份试点曾生成不自然的 PostgreSQL 比较题。本轮保留第一批不动，新增[角色清单与拒收记录](../../../llamaindex-retrieval/statetune/retrieval-v2-20260923/SOURCES-CURATED.json)：V2 累计训练 122、开发 15、盲留出 13 个仓库族，明确拒收 4 个角色不符项目。再增加直接可比的盲留出来源 11 个，以及训练来源 30 个，形成[V4 完整清单](../../../llamaindex-retrieval/statetune/retrieval-v4-20260924/SOURCES-CURATED.json)：训练 **152**、开发 **15**、盲留出 **24**，共 **191** 个仓库族；清单 SHA-256 为 `e3c88a03e0694455770f2ca0878914d9bf5da39c29d5a7c909fcdd4e5b4e6afa`。本机全部 191 份 README 的 SHA-256 与 Git blob 身份通过复核；源码、完整原文仍在忽略目录 `data/`，可用[按固定 blob 重建脚本](../../../scripts/retrieval_statetune/rehydrate_readmes.py)恢复。

[证据块索引](../../../llamaindex-retrieval/statetune/retrieval-v4-20260924/EVIDENCE-BLOCKS.json)来自这 191 份 README，记载 **8,394** 个精确字节跨度及标题路径，原文字节回放校验通过。其中训练分区有 6,745 块。它是待标注材料库，**0 条**已标注支持/不足/冲突；切块数不能写成证据训练样本数。GitHub 仓库代码许可元数据只用于来源筛选，并非 README 文本商业训练授权结论。

## 2. 规划草稿及准入审计

在已登记来源和提示下，DeepSeek Flash 仅作为起草教师，原始请求、响应、局部失败、费用收据都保留在本机 `data/quality-runs/retrieval-state-v2-20260924/`，凭据未进入仓库。此前 V2 盲题提示的 128 个位置只有 15 条绑定成功，主要把数组写成字符串；原失败见[失败收据](../../../artifacts/retrieval-state-data-20260924/BLIND-PILOT-v2-FAILURE.json)，没有回填为成功。改成显式 JSON 契约后，[V3 盲题草稿收据](../../../artifacts/retrieval-state-data-20260924/BLIND-PILOT-v3-SUMMARY.json)为 124/128 结构绑定，但仍把充电软件、摄像头分析和家居控制器放在同一能力轴，故没有冻结盲集。

收紧比较来源后，V4 盲题草稿为 **127/128** 条结构绑定；[逐条候选与统计](../../../llamaindex-retrieval/statetune/retrieval-v3-20260924/BLIND-CANDIDATES-SUMMARY.json)仍标出 15 条 `missing` 没有明确缺口请求、16 条 `conflict` 没有明确同项目同版本范围，还有 1 条把内部分组名写进问题。**这些不是已验收的 120 道盲题。**

训练分区的 V4 标签先行起草产生两批未审读规划草稿：[原 122 族批次](../../../llamaindex-retrieval/statetune/retrieval-v3-20260924/PLAN-CANDIDATES-SUMMARY.json) **2,174** 条，追加 30 族批次 **1,096** 条，合计 **3,270** 条，覆盖 152 族。11 个任务的教师输出结构失败留在原运行结果中；不是 11 条答案失败。合并后归一化问题逐字唯一率为 100%，但最大来源族参与占比为 **2.87%**，超过预设 2% 上限。3,270 条均可编译为精确 RWKVoS batch 提示与只监督目标/EOS 的 token 行，最长 1,130 token，mask/EOS 逐行核对通过；[token/准入收据](../../../llamaindex-retrieval/statetune/retrieval-v4-20260924/TOKEN-AUDIT.json)明确拒绝：3,270 条无独立语义审读，规划外的证据判断与补查角色各为 0，完整目标 5,000 未满足，比较类候选仅 515，来源集中度也未过关。**格式可编码不等于可训练。**

为方便逐条审读，[机械待审队列](../../../llamaindex-retrieval/statetune/retrieval-v4-20260924/PLAN-REVIEW-SHORTLIST.json)仅挑出 **2,300 个候选 ID**：先把 279 条缺口问法不明确、445 条同范围冲突问法不明确的草稿留在待修区，再按来源参与次数平衡；152 族均被覆盖，最大占比恰为 2.00%。队列题型分布：普通 677、比较 496、选择 490、历史修改 407、缺口 224、冲突 **6**。这显露冲突材料严重不足，也说明机械筛选不能当成语义准入；队列每条仍 `review.accepted=false`，准入训练数为 **0**。

## 3. 自然问法方向试点

标签先行会强迫问题逐字列出计划维度，很多题像专业检查表，且历史修改题有时把撤回条件重新带回。用同一组 12 个新来源任务尝试“先写自然场景，再规划待查项”：V5 只绑定 **24/96** 条，主要是教师只选择相关项目，而旧编译器强制全组项目；V6 改为每题按最新问题逐字登记实际提及的项目并保留原始教师输出，绑定 **65/96** 条。[V6 逐条候选与失败统计](../../../llamaindex-retrieval/statetune/retrieval-v6-20260924/PILOT-SUMMARY.json)仍有 19 条历史为空、12 条项目数不符。作者抽看发现自然场景更贴近日常选型，但仍有题型错配、未登记项目简称与条件归属问题，**未过语义门槛，也没有扩量**。V5/V6 改了提示和绑定方式，不是单变量模型质量对照。

## 4. 下一步数据门槛

1. 对 V6 自然问法及 V4 2,300 条待审队列做逐项语义复核：实际项目角色、问题与计划维度、历史撤回、来源范围、条件归属。教师自审不算独立复核；不能批量把 `review.accepted` 改成 true。
2. 新建有真实同范围矛盾和缺材料执行状态的材料，不能把不同产品的差异标成冲突。冻结至少 120 道新自然盲题及来源快照；当前 127 条只是候选，旧题继续全量回归。
3. 在实际运行提示和取证契约稳定后，分别准备至少 1,800 条单格证据判断、800 条缺口补查的逐字标签。来源尚未搜索、供应商失败和资料读后不足必须分开；不从 README 块数量推断标签数量。
4. 通过[现有准入审计](../../../scripts/retrieval_statetune/audit_candidates.py)与独立语义审读后，才有可供训练的数据。用户本轮明确不训练，因此没有启动 GPU、StateTune 或正式服务切换。

验证：数据准备相关的单元检查、精确哈希复核、token mask/EOS 核对和 Ruff 均通过；这些工程检查只证明数据绑定与格式，不证明检索或回答体验改善。
