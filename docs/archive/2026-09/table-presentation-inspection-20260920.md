# 表格呈现检查：解码参数、重复表头与下一项对照

历史检查记录，2026-09-20。当前状态见 [CURRENT](../../CURRENT.md)。本轮检查代码和原始 trace，并运行本地结构复现；**未调用模型、未修改应用或部署、未认定新的呈现方式更好**。

## 1. temperature 在当前专用服务中不影响选词

[7.2B 专用评测服务](../../../llamaindex-retrieval/eval/g1j72-20260920/serve_72.py) 的生成循环直接执行 `token = int(logits.argmax())`，没有用 temperature 缩放 logits，也没有概率抽样。请求中的温度值不参与解码；top_k 同样不参与，top_p=0 只作为请求接受条件。准确表述应是“固定贪心解码”，而不是“用温度 0 控制随机性”。

客户端仍会把 temperature=0 映射为传输参数 0.001，这是接口行为，不是本次实验的有效干预。即使对 logits 除以有限正温度后再取 argmax，数学上的最大值排序也不变；这里的实现更直接，完全没读取温度。此前标签对照仍成立，因为两组使用同一贪心实现；实验没有验证任何温度效果。

该结论只针对这台专用服务的代码，不扩展到其他 RWKV 服务或采样实现。冻结历史脚本/trace 不改写；维护文档更正术语。

## 2. 实验呈现和应用 Reader 呈现不一样

上一轮 strict-v1 实验在一行 JSON 中序列化 source、question、contexts 和 text。模型实际看到的上下文换行是反斜杠加 n，而不是展示界面渲染后的 Markdown。下面仅摘录数据部分：

```text
"contexts": [{"text": "# 棣山 C26\n| 模式 | 续航（小时） |"}], "text": "| 省电 | 48 |"
```

[应用 Reader 函数](../../../llamaindex-retrieval/src/llamaindex_retrieval/reader_prompt.py) 则先输出 JSON 格式的父级上下文，再直接展开参考原文：

```text
父级上下文：[{"text": "# 棣山 C26\n| 模式 | 续航（小时） |"}]
参考原文：
| 省电 | 48 |
```

两种路径都需要模型跨字段关联表头和行，但序列化格式、问题位置和指令主体并不完全相同。不能把前者的实验成绩直接当作后者的验收。

另外，上轮 16 条表格材料都未包含 Markdown 的分隔行 `| --- | --- |`；它们是在测试表头/行关联，不是完整标准表格。真实 verbatim 切分器识别完整表格时，会保留该分隔行。新验证材料应覆盖完整表格与缺少结构的材料，并预先分层；不能给旧样本补上分隔行后当作单纯的位置变化。

已保存[已知失败的准确 prompt 与展示预览](../../../artifacts/table-presentation-inspection-20260920/known-failure-view.json)。预览没有调用模型，没有得到新的语义结果。前端显示转义字符与否，也不能代表服务实际发送的文本。

## 3. 已确认缺陷：原子证据重复附加同一表头

在当前代码的原子证据路径中：

1. `verbatim_nodes()` 把完整表格作为一个 chunk，并在 metadata.context_spans 中记录标题、表头和分隔行。
2. `short_spans()` 在 chunk 内选择单行时，再把本地表头和分隔行作为 context。
3. `candidates()` 无条件追加 metadata.context_spans，没有合并同一来源范围。

因此，普通完整表格的数据行会带上两份表头。这是同一原文范围重复出现，不是两个独立来源支持。

实际执行[只读复现脚本](../../../llamaindex-retrieval/eval/table-presentation-inspection-20260920/inspect_layout.py) 得到：

| 构造材料 | 观察 |
| --- | --- |
| 普通两列表格 | 数据行上下文中完整表头出现两次 |
| 30 列宽表 | 唯一父级上下文 459 字符，重复后 909 字符 |
| 同一宽表的数据行 | 行长不超过 600，但因上下文超过 600，被 candidates() 过滤；尚未进入模型 |

宽表结果剩一个候选（表头），答案所在的数据行被排除。此处的丢失是预算过滤行为，不能靠更换模型修复；未测试模型看到该行后是否会正确回答。

复现使用合成文档调用当前代码，不等于已确认线上用户数据受到相同影响。该缺陷位于原子证据路径；不能据此推断所有正式问答路径都存在同样的重复。上轮固定材料绕过了 candidates()，因此**不能用这个缺陷解释上轮四个短表格漏选**。

完整证据见[结构检查结果](../../../artifacts/table-presentation-inspection-20260920/inspection.json)。

## 4. 建议的修复与实验顺序

### 第一步：先修复重复上下文，单独验收

按同一来源版本的原文范围合并重叠的表头引用，保留稳定的来源、偏移和内容哈希。不能简单按字符串去重，因为不同表格可能恰好有相同表头；也不能把 chunk 内相对偏移与文档绝对偏移直接比较。计算预算和构造模型输入必须使用同一份规范化上下文，不通过提高上限掩盖重复。

必要验证：普通完整表格只附带一次表头；宽表的答案行不再因重复而丢弃；不同来源/范围的同字表头不会合并；标题层级、行偏移、原文哈希与字符内容保持一致；真正超限的结构仍明确报告。此修复不承诺召回提升，先做结构正确性验收。

### 第二步：冻结一次呈现格式实验

修复与呈现实验分开提交，不在同一组对照中同时改变切分、去重、标签和模型。

- 基线：现有 strict-v1 + ANSWERABLE/INSUFFICIENT + 分字段 JSON。
- 候选：固定问题、来源、指令、标签、字段顺序及全部证据字符，仅把 contexts/text 的内容改成带明确边界的逐字多行展示。仍区分上下文与目标片段；不追加猜测的字段名、单位或事实句。
- 该对照测的是“证据序列化呈现”，不是纯粹位置变化。JSON 包装/转义会一起改变，报告不能进一步归因于某个符号；需要时再开更细的对照。
- 不把表头合入原文快照。展示是单独的可审计视图，原始 text、context、ID、偏移和哈希不动。
- 材料须预先覆盖完整表格、只有表头、错误行/列、错误对象/范围、空值、零值、否定、正文与引用指令干扰。完整/不完整表格分层统计。
- 所有旧 40＋24＋160 条只能作已见回归；新模板用于验证。未经过独立复核时继续明确标注限制。
- 固定 7.2B zero State、greedy argmax、输出预算、原文、次序控制及精确解析规则；保存最终线上格式的 prompt 与内容哈希。重复轮只测稳定性。
- 同时报误选、漏选、非法输出、成对正确率和逐类退步；不能只挑表格召回。候选晋级仍要求零误选、零非法输出、召回和成对正确率至少 90%，且需有事前登记的总体比较标准。

这是具体设计，**数据、候选边界语法、运行顺序和统计门槛尚未冻结，模型对照尚未执行**。本轮不凭展示预览宣称优化有效，也不改动冻结的旧实验。
