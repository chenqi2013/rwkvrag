# 本机实时检索质量诊断（2026-09-23）

## 范围与绑定

以提交 `9e19bfa2`、本机 API `127.0.0.1:18440`、SearXNG `127.0.0.1:18448`、索引 `rwkvrag-local-use-v1` 运行。配置仍为每次网络查询最多 2 条结果、一次回答最多 2 条网络查询；未改代码、模型、索引或配置。[V1 固定题与口径](../../../llamaindex-retrieval/eval/live-retrieval-20260923-v1/README.md)和[25 次原始调用](../../../artifacts/live-retrieval-20260923-v1/RUN-v1.json)覆盖 3 道单项目题、8 道两至四项目比较题、8 次引擎原始前 10 条对照、4 次混合检索和 2 次自动路由。[V2 固定诊断](../../../llamaindex-retrieval/eval/live-retrieval-20260923-v2/README.md)与[7 次原始调用](../../../artifacts/live-retrieval-20260923-v2/RUN-v2.json)包括 6 条按项目拆问和 1 次完整三项目问答。两轮共 32 次调用 HTTP 均为 200；响应和哈希未事后改写。

这是实现者人工审读的检索诊断，没有独立 Gold、盲审或 Tavily 同题对照。网络排序随时间变化，下列比例仅描述这批题与本次部署，不能作为总体准确率。

V2 在不加 `site:` 限定、仍保留每题 2 条结果的条件下，把原比较题拆成单项目自然问法：`llama.cpp`、Dify、WeKnora 的对应官方资料进入前 2 条；vLLM、SGLang、RAGFlow 仍未进入。这说明项目拆问有潜力，但仅拆问还不足以保证官方来源覆盖，且 6 条测试与 V1 的整句题不是同分布准确率对照。

## 完整问答失败链

强制 `web` 询问“vLLM、SGLang 和 llama.cpp 在部署方式、硬件需求和推理优化上分别适合什么场景？”时，当前正式 2.9B 模型的规划器两次都生成 9 条查询（每项目 3 条属性），超过 `native_max_queries=6`；两次解析均报 `invalid query count`，最终回退到原始整句。网络只交给后续阅读两条二手摘要。阅读器选中其中一条知乎摘要，长度 90 字，内容只有“硬件适配”和决策表表头，并无三个项目的具体硬件、部署或缓存对照。

Writer 仍用这条材料写出三个项目的具体场景、单卡/多卡和内存池化结论，三段都引用 `[资料 1]`；接口 `generation.status=planner_partial_failure`，`evidence_count=1`，`citation_audit.semantic_support_verified=false`，耗时约 25.7 秒。现有引用审计确认编号存在，却没有验证结论受到该摘要支持。**这是这次最直接的用户可见质量失败：检索缺口经过规划回退和阅读误选，最终变成带有效编号但无语义支持的比较答案。**本次没有独立逐项 Gold，因此不把每个技术判断再额外判为事实真伪；“该引用无法支持这些细节”已可从原材料逐字核对。

## 判断与下一步

目前 SearXNG 的可用性合格，但自然多项目比较的检索质量未通过。主要瓶颈按本次链路顺序是：`auto` 路由漏判、规划数量上限与三项目多属性问题冲突、整句搜索偏二手、每查询两条且无官方资料覆盖、只取摘要、混合检索没有过滤无关背景语料，以及引用校验不检查语义支持。不能将任何一个单点改动直接宣称能修好最终答案。

下一轮应先固定同一批新题与源快照，分阶段做受控诊断：① 路由与规划分别核验，规划按项目合并属性后验证仍不漏需求；② 比较整句与逐项目搜索的官方资料覆盖和延迟；③ 加入受限正文抓取，验证来源原文、版本和引用位置；④ 在同样候选中测知识库相关性过滤与来源配额；⑤ 最后用相同原始材料看 Resolver、Writer 和引文支持，普通题同步回归。每阶段分开报告，避免把外网波动、配置变化和模型变化混算成收益。无需先购买新的搜索 API；当前问题不能由换 Key 单独解决。
