## 当前行为

管理页默认“自动判断是否联网”：复用本地 `/home/chase/GitHub/RWKV-SearchReader` 的联网分类提示词和 1.5B StateTune 模型。分类器只读取问题和对话历史，不读取知识库检索结果。输出 true 时运行知识库＋网络，false 时只检索知识库。

用户也可明确选择仅知识库、知识库＋网络、仅网络。手动模式跳过分类器。分类失败会返回 routing_failed，停止后续流程，界面允许重试或手动选择；不会把分类失败当成允许联网。

API 使用：

```json
{"question":"内部升级计划是什么？请同时查询厂商最近的公告。","retrieval_mode":"auto","knowledge_base_id":"default"}
```

`POST /v1/ask` 生成回答并保留运行历史；`POST /v1/search` 仅返回检索材料与轨迹。`retrieval_mode` 接受 auto / knowledge_base / hybrid / web。为兼容既有调用者，API 不传该字段时仍为 knowledge_base；新管理页默认发送 auto。知识库过滤只约束本地检索，不约束网络范围。

## 集成方式

- 使用 SearchReader 自己的虚拟环境，通过有并发数、时间和输出大小上限的子进程调用其搜索与网页获取模块。未修改该项目已有未提交代码，也未复制其搜索密钥。
- 本次实际搜索后端是 Tavily；沿用 SearchReader 原有 provider 配置、查询处理和网页获取行为。没有把另一套模型生成的回答当成证据导入。
- 两类材料统一转换为来源记录，再交给现有 RWKV Reader 选择逐字证据、Writer 生成回答。原始模型输出不被代码改写。
- 网络来源保留 URL、抓取时间、网页标注日期、原始材料快照及哈希、实际用于阅读的材料哈希、提供方与代码哈希。搜索摘要和受材料预算限制的内容会标注。
- 同一 URL 的相同阅读文本合并，保留各次抓取观察记录；内容不同的材料分别保留。不同提供方的分数不直接比较，混合候选按提供方交替排列，再受 Reader 预算约束。
- 网络模式保留完整原问题作为额外检索和阅读任务，同时保留规划器原输出，避免代码覆盖或伪造规划结果。
- 当前每次最多 2 条网络查询、每条最多 2 个结果、每结果最多 3,000 字符进入 Reader；完整 provider 材料另存快照。超出查询预算的任务在 trace 中标记 skipped_query_budget。预算不代表证据完整性保证。
- 一侧检索失败时可用另一侧证据继续，但标记 retrieval_partial_failure；两侧都失败时不调用 Reader/Writer。失败与原始回答分开记录。

联网会把检索问题发送给搜索提供方，不直接上传知识库文件。历史中的信息可能影响模型生成的检索问题；需要严格限定离线时可手动选择仅知识库。

## 验收结果与真实失败

证据目录：`artifacts/hybrid-search-20260919/`。

- 175 项相关后端测试通过，覆盖模式隔离、历史路由、原始输出保持、单侧失败、全部失败、子进程超时回收、快照保存、网页去重、查询预算及完整问题保留。使用桩的测试只证明工程行为。
- 25 项前端测试通过，TypeScript/Vite 构建通过，既有大包提示仍在。
- 实际调用 SearchReader / Tavily 获取到 Python 官方网页。
- 实际浏览器在隔离数据库和索引上传虚构内部计划，自动分类后同时读取知识库与网络证据。最终样例回答两个日期正确，但语义质量验收未通过，见下文。
- 上线后浏览器确认默认自动模式；只读调用验证自动不联网时 web_search 为空、指定联网时只返回网页材料；原有 46,051 个业务索引切片保留。未向业务知识库上传虚构验收资料。

保留三次开发验收的原始记录：

1. 首次：规划器遗漏内部问题，重复网页材料导致 Writer 输入超预算。
2. 修正去重与预算、保留原问题后：执行完成，但 Reader 仍漏选内部证据，回答只覆盖外部日期。
3. 将问题明确表达为两个独立问句后：两类证据均进入 Writer，两个日期正确；但第二句话引用编号错误地指向内部文档，网页证据还是镜像站而非用户要求的官方域名。

因此 **集成链路通过，不等于回答语义验收通过**。没有修补最终回答或改写引用。`manual-answer-review.json` 记录判定，`live-hybrid-answer*.json` 保存原始模型响应与来源。这些是已暴露开发样例，不是盲测。
