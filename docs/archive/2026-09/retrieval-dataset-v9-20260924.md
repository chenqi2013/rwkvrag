## 机械核验

[V9 审计收据](../../../llamaindex-retrieval/statetune/retrieval-v9-20260924/AUDIT.json)和[重放核验器](../../../scripts/retrieval_statetune/verify_review_queue_v9.py)对 5,462 行重新检查：提示/目标哈希，191 份 README 的 SHA-256、每段来源的字节跨度和引文，仓库族分集与旧题禁入哈希，规划目标结构，补查格子/搜索式，完整 RWKV token 编码、只监督目标的 mask 及 EOS。**5,462/5,462 机械通过，最长 1,130 token；这些都不证明目标语义正确。**

审读队列覆盖 152 个训练仓库族，最大单族占比 **1.996%**，归一化问题唯一率 **94.31%**。六类计数：普通2,284、比较1,122、选择825、历史577、缺材料500、同范围冲突**154**。前五类过预设数量，冲突低于300；审计同时明确拒绝所有行，因为缺独立语义复核。来源仓库代码许可证元数据不能推出 README 文本可商用训练，商业授权须单独确认。旧题排除只覆盖登记哈希/族；仓库别名、转载和语义近似仍需人工检查。

## 发现的关键质量问题

1. 首个单来源证据批次让普通题几乎全是 `supported`、比较题几乎全是 `insufficient`。如果直接训练，模型可能仅凭题型拒答。因此 V8 增加双来源比较支持、普通题不足和同题不同摘录对照；V9 审读队列为普通支持700、普通不足654、比较支持239、比较不足224，另有选择不足121、缺材料不足96。**结构平衡不等于语义平衡。**
2. 两来源配对教师经逐字引文检查后仍大量错选证据。作者以固定随机种子 `92024` 从 V9 所选的 239 条 `v8-pair*` 比较支持候选中抽 24 条逐项看问题与两段引文：8 条可直接支持、1 条只支持部分范围、**15 条至少一侧不支持所问维度**。例如 `v8-pair199:0` 问两工具默认隐藏文件处理，ripgrep 的引文却是 PCRE2；`v8-pair057:0` 问双方 PATCH API 兼容性，vcpkg 的引文是许可证。这是作者抽检、非独立盲审，不能外推精确总体错误率，但足以阻断配对正例直接训练。抽样中明确错配的 ID：`v8-pair162:0`、`061:0`、`240:0`、`197:0`、`020:1`、`199:0`、`228:0`、`195:1`、`237:0`、`218:0`、`320:0`、`241:0`、`168:0`、`203:0`、`057:0`；`185:0` 为范围不完整。它们原样保留供审读，**没有改标为正确或准入**。
3. 同范围冲突仍缺：当前官方 README 单版本摘录很少能给出同一项目、同一版本/条件下互相矛盾的两条记录。把产品 A/B 差异标为冲突或以模板批量凑 146 条会训练错误边界，本轮没有这样做。
4. 补查训练候选 878 条是从规划格子构造的“未搜/尚无已验收证据”模拟状态，另有 150 条空工作表停止。它们没有真实搜索执行日志；教师搜索式虽做对象名与重复检查，是否真能带来新信息未经实时检索验证。开发/留出分区尚无对应补查标签，也未冻结 120 道新盲题。
