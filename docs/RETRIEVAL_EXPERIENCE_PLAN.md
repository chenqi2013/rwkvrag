# 检索体验改进方案

2026-09-20。**状态：设计草案，尚未改变运行中的问答链路。**
用户明确：目标是让检索体验更好。评测用于发现问题和保护已有能力，不能代替真实使用验收。
运行与实验状态见 [CURRENT](CURRENT.md)，分层语义契约见 [RELIABILITY_PLAN](RELIABILITY_PLAN.md)。

## 一次查询应该让用户获得什么

1. 问的内容被理解，包括最后确认的对象、版本、时间、条件和字段。
2. 很快看到系统正在做什么；长任务可以停止，失败后可以重试且不丢问题。
3. 答案覆盖实际所问，数值、单位、否定和适用条件保持完整。
4. 每项结论的引用都能打开正确的原文位置；缺证据、冲突和处理失败看得清。
5. 用户能指出具体哪一项有问题，反馈能定位到当时的回答和来源版本。

首页的核心内容应是“提问—回答—依据”，运行参数和模型 trace 放入可展开的诊断区。
检索模式（仅知识库/允许联网）影响用户的实际选择，应保持可见。

## 第一批：问题与搜索表达分离

**用户得到的改变：** 搜索了很多近义词之后，回答仍只围绕原本想确认的内容；
同一段不含地址的标题不会因为另一种搜索写法就成为地址依据。

- 保留最新有效任务和逐项问题；对象、属性、版本和条件由模型理解，代码只校验结构。
- 搜索表达绑定到对应项目，用于找候选材料，不直接替代该项目的证据核验问题。
- 原文观察与问题匹配分别留记录。Reader 的NO只说明该次判断未确认支持，不能写成
  “全库没有”“事实不存在”或“数值为零”。
- 同一项目、同一原文版本的重复候选只按稳定身份去重；不按关键词或测试题型决定真假。
- 沿用已有 task-matrix 的单项目问题、缺项追查和调用预算结构，先核对其契约与失败案例，
  **不直接开启整个功能开关**。否则会同时改变规划、检索、核验和写作，无法判断收益来自哪里。
- 普通单项查询也走同样的语义契约；不能为了对比题单独堆一条只适用于某些实体的规则链。

第一项对照只改变“证据判断绑定到哪个问题”，模型、State、Writer和检索候选保持固定。
这一步可能降低误选，也可能增加漏选，必须对旧题逐项查退步。通过后再测减少冗余检索和
模型调用的收益，不能把更快直接当作更正确。

## 同批独立交付：用户能看进度、能停止、能重试

这部分先保持语义调用输入不变，作为独立的运行与交互改造：

- 查询创建后返回稳定的运行ID；页面展示“理解问题、查找资料、核对资料、组织回答”
  等实际阶段及已完成项目，不显示编造的完成百分比。
- 断开或刷新页面后可按运行ID恢复观察；同一任务重试创建新尝试，不覆盖原答复。
- 点击停止后立即显示“已请求停止”，停止继续派发该任务的新调用，并保存已有 trace。
- 当前 `RwkvosBatchClient` 对已派发的共享批次取消，记录为 `shared_batch_continues`。
  因此不能只加一个前端 AbortController 就宣称 GPU 推理已停止；要区分应用停止调度、
  提供方是否支持取消、底层任务何时结束，也不能取消同批次其他用户的调用。
- 达到输出或任务预算时明确显示本次未完成，保存完整原始输出和失败阶段。
  不截掉重复句后把剩余文本伪装成成功答案；不由代码补写拒答、补引用或改单位。
- 状态和操作提示由运行事实驱动；模型的“缺证据/冲突”判断仍与运行失败分开。

交互验收以实际操作为准：提交后一个正常请求往返内出现可观察的运行；停止操作有即时
确认；停止后不再新增该任务的派发；刷新可恢复；重试不丢历史。具体模型完成耗时要在
完整基线结束后再制定承诺，不能现在写一个未验证的“几秒回答”。

## 第二批：原子—关系—分层回答服务于完整答案

保持用户提出的方向，但每层有明确职责：

```mermaid
flowchart LR
    Q[用户实际所问的项目] --> S[检索候选]
    S --> O[单份原文观察\n对象 值 单位 条件 否定]
    O --> A[独立判断是否支持该项目]
    A --> R[同一项目内的关系\n一致 不同范围 冲突 明确修订]
    R --> W[逐项回答后汇总\n保留缺项和来源依赖]
```

原子层不能把“64位元组”理解为“64位元”；关系层不能把不同模式当成同范围冲突；
总结层不能在缩写时丢掉条件，或重新裁定未解决的冲突。逐字范围校验只证明抄到了原文，
不证明语义理解正确；三层都要保留各自的原始模型输出与独立判断。

优先打通真实问题的一条完整路径，再考虑扩展层数和 StateTune。短任务是否更可靠、
更多调用是否值得，都以实际答案、等待时间和可追溯性验证。

## 用哪些真实使用过程验收

保留既有题目作为回归，并在实际界面完成下列操作。它们是用户旅程，不新包装成大量
换名字、换数字的独立测试能力：

| 使用过程 | 用户可观察的完成条件 |
| --- | --- |
| 普通事实/定义/地点/列表 | 问什么答什么；信息完整；列表不混入别的版本；可打开支持原文 |
| 多对象多字段，包括单位和否定 | 每个所求项目有答案或明确缺项；对象、条件和单位不串位 |
| 对话中撤回或更正范围 | 沿用最后有效要求，旧服务器版、旧字段等不重新混入 |
| 资料冲突、明确修订、未记载 | 能区分三者，看到分别依据；没有证据时不编造编号 |
| 需要联网补充但网络失败 | 告知该来源未完成，保留已获取的知识库依据，不把网络失败说成事实不存在 |
| 长任务停止、页面刷新、重试 | 可恢复运行状态，停止不误伤其他任务，失败原答复和新尝试都能查看 |
| 用户指出某一项或某个引用有错 | 反馈绑定运行、结论及来源版本；不自动覆盖原文或把未核验反馈当训练金标 |

记录用户完成查询所需的等待、补问和重试次数，以及是否拿到完整可用的答案。
后台评测负责发现普通题退步、漏证据和误引用；不以总分抵消一个关键使用过程的失败。
