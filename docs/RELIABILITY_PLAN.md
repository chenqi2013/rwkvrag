# 主线：可靠证据 → 关系判断 → 分层回答

维护日期：2026-09-20。这是实施顺序与验收设计；实际完成状态以 [CURRENT](CURRENT.md) 为准。遵循[架构规则](../llamaindex-retrieval/ARCHITECTURE_RULES.md)。

## 目标与当前阻塞

**首要目标是修复对比、选择类检索，并使较小模型能独立完成这些任务。** 用户的实际起点是：
原先较大模型在普通题上准确率较高，但前端实际使用暴露了对比、选择时答错、反复比较、
输出无法收尾的问题。普通题分数不能代表这两类能力。较大模型用于参考对照，小模型是
需要独立跑通的产品路径，不能暗中依赖服务器上的大模型补答。

**用户最新指定7.2B作为主线模型。** 后续对比、选择流程以7.2B独立完成为目标，
2.9B保留历史基线与轻量化对照，不再作为主线必须达到的模型容量。
7.2B沿用本地优化vllm-rwkv引擎；模型身份、State和资源需求以实际配置核对为准。
不能直接套用2.9B的Reader/Writer State，也不能仅更改模型名称就声称迁移完成。
用户提及的原13.3模型普通题表现属于历史经验，尚未在本轮按相同语料与架构重测。
先固定模型比较架构，再固定架构比较模型，避免把两种收益混在一起。

最终验收是用户能否完成查询：比较项目齐全、选择依据满足实际条件、回答能够收尾、
引用可核对，同时普通题能力保持。[体验方案](RETRIEVAL_EXPERIENCE_PLAN.md)中的进度、
停止与恢复是辅助交付。已完成的隔离交互候选暂不继续扩展；扩大回归用于保护已有能力，
不再用评测规模代替比较/选择主线的实施。

用户提出的主线是原子化、分子化、阶梯式总结：避免让 RWKV 在一个长上下文里反复比较多份冲突材料。每次调用承担一个有边界的任务，来源、条件和未解决问题逐层保留。

当前已有的是面向单属性的原文记录与引用位置，还不是可靠的标准化原子事实。最新同引擎回归仍有表格关联、否定证据和输出协议问题。先解决第一层的误读，才能评价上层是否真正减少冲突处理成本；不能将错误的 Reader 判断作为已裁定事实传给分子层。

## 下一步先打通两个完整使用过程

### 对比：相同条件下逐项回答

1. 模型理解对象、维度、版本与适用条件，形成“对象×维度×条件”的任务格。
   对话中的最新更正继续保留，不由关键词规则猜测。
2. 每格从短原文获取值、单位、条件、否定及逐字依据；观察与问题匹配分开记录。
3. 同一维度下核对条件后再比较。不同模式、版本或统计时间不自动当成冲突。
   缺项继续保持缺项，未解决冲突继续显示双方依据。
4. 先完成少量逐项结论，再生成整体对比；高层不重新读全部混合材料来反复裁定。

### 选择：按用户条件给出可解释结论

1. 模型区分候选对象、必须满足的条件和用户表达的偏好；未给出的权重不自行编造。
2. 逐候选、逐条件判断满足、不满足或证据不足，并绑定依据。
   材料未写某属性不能当成不满足，也不能当成满足。
3. 在同一条件和版本范围内汇总可选项、排除原因及待确认事项。
   无足够证据支持唯一选择时，保留条件化建议或必要澄清，不硬选一个“最好”。
4. 回答同时给出决定依据及其引用；逐层保留反例和限制条件。

这两类任务包含一致资料、条件差异、缺资料与真正冲突，不能只测冲突场景。
先完成一个有多条件的对比和一个带硬条件/偏好的选择流程，再逐层扩展。
现有普通题与旧失败项保留，不能为了这些流程删题或关闭旧功能。

## 小模型与资源约束是架构目标

- 语义任务缩小到一次处理少量对象、一个维度或一组条件；输入规模、输出上限和追加
  检索次数都有边界，防止无界反复比较。
- 来源版本不变时可以复用已保存的原文观察，减少重复读取；不能把先前的支持判断
  无条件迁移到另一个问题。
- 比较和选择优先按候选×维度组织，避免对每两份材料都进行无界两两比较。
- 模型大小、精度/量化、State、上下文占用、峰值显存/内存、总调用数和等待时间分别记录。
  参数量较小不自动等于普通硬件可用；尚未测得的最低硬件要求不作承诺。
- StateTune在任务协议和失败类型稳定后再做；训练数据保留独立复核依据，不能把模型
  自己打的YES标签直接当作正确金标。

Reader的“用户任务/搜索表达”绑定候选仅用于诊断误选机制，不等于比较与选择链路已修复。
完整用户任务绑定也不是最终逐格协议，不能为等待该局部实验而继续后置核心流程设计。

## 分阶段交付

| 阶段 | 模型承担的任务 | 代码承担的任务 | 通过后进入哪里 |
| --- | --- | --- | --- |
| 1. 单份证据理解 | 给定问题与一份短原文，判断能否回答；随后另测字段提取 | 保存来源版本、精确范围、父级上下文、原始输出与运行状态 | 新材料复验、独立 assessment 接入 |
| 2. 标准化原子记录 | 提取对象、属性、值、单位、条件、否定与修订信息，并为字段指向原文 | 校验引用范围和逐字一致性；保留无法提取和判断失败 | 同属性关系评测 |
| 3. 关系分子 | 判断少量原子记录是相同、不同适用范围、冲突、明确修订关系或信息不足 | 根据已有字段检索候选关系、限制输入规模、保存边与原始 trace | 单属性对比结论 |
| 4. 阶梯式总结 | 先总结单属性，再总结跨属性结论；保留冲突和缺证据 | 固定依赖图、预算与引用映射，执行审计 | 真实检索端到端验收；之后才评估 Wiki 更新 |

“不同适用范围”与“冲突”必须分开：标准模式 12 小时、节能模式 24 小时不自动构成冲突。来源间的权威和新旧采用也必须有单独证据，不能按文件日期或数值大小写规则决定。

## 已完成的第一步：呈现方式对照

在已验证的本地 vllm-rwkv / G1j 7.2B 上，固定 zero State、top-1、strict-v1 判断语义、标签、模板和预算，仅比较原 JSON 与有边界的逐字多行序列化。保留相同字段顺序和原文字符，不增加“应该选中”的提示，不添加示例，不做表格转自然语言的语义改写。

例如对象标题与表头、数据行都保留其原有身份：

```
父级上下文原文：
设备：示例 A
| 模式 | 转速（rpm） |

行原文：
| 静音 | 1200 |
```

上例只解释设计意图；正式实验的精确边界语法以[冻结方案及脚本](../llamaindex-retrieval/eval/reader-presentation-20260920/README.md)为准。不能把表头单独当成值，也不能由代码把它推断成“示例 A 的静音转速为 1200 rpm”。

本轮 160 条已见材料、两组各两轮，共 640 次调用，属于诊断回归。先核验基线与前轮输入 token 完全一致，再计算表格收益、其他类别退步、误选、非法输出与重复稳定性。原小样本晋级门槛继续保留，不因某一类别好转而降低。

结果已完成：表格命中 0/8→5/8，但新增 3 条属性误选、4 条否定 QA 漏选；整体仅净增 1 条正确，改善门槛未通过，候选未接入。见[完整报告](archive/2026-09/reader-presentation-results-20260920.md)。这项结果支持继续研究证据输入与任务拆分，但没有证明某种格式或更复杂架构整体更好。

## 下一项：先设计字段绑定与独立判断

下一项不继续根据这些失败搜索格式，也不按题型选择“哪种格式成绩更好”。先冻结两种不同职责：

1. **原文观察**：一份证据究竟记载了哪个对象的哪个属性，值/单位/条件/否定是什么；字段指向原文。预约量不能被命名成发货量，明确“没有”不能被丢掉。
2. **问题匹配**：独立 assessment 比较用户所问与观察记录是否匹配，仍可查看绑定原文；输出支持、不支持或运行失败，并保留独立 trace。不能让结构完整自动等于语义支持。

先提交字段契约和错误分类，再准备训练前的新评测材料；字段抽取自身也必须评测，不假设拆开之后自然正确。数值复制、范围定位、否定保留、无证据处理、字段间一致性以及额外调用成本分别计分。具体 prompt、输出预算和晋级阈值尚未冻结，不在本次呈现实验里追加执行。

## 接入时必须跨过的边界

目前应用的 `AtomicEvidenceService` 在选择后调用现有 2.9B Reader450，使用 `binary_query_prompt`，与实验里的 7.2B zero State / strict-v1 并不等价。实验胜出也不能直接声称应用已修复。

接入顺序：

1. 冻结新材料，覆盖表头无行、错行、错对象、单位/范围、缺失值与零值、否定、修订和攻击文本；旧材料只作回归。说明标注人及独立复核是否完成。
2. 按 [ASSESSMENTS](ASSESSMENTS.md) 新建独立判断记录，与原文快照分离；记录协议、模型、State、解码、输入 token 和调用身份，不覆盖历史判断。
3. 先在固定材料上验收新适配器，再分别验收候选选择和真实检索，最后进入带引用的对比回答。每一步固定其他组件。
4. 真实浏览器验收原文、条件、历史版本及处理失败能否看清；执行完成不能展示成事实已经核实。

## 原子、分子与总结的约束

### 原子记录

字段拆分设计：`target` 是用户查询目标；`observed_object / attribute / value / unit / conditions / polarity / revision` 是模型提取结果，两者不能混为一谈。每个提取字段关联原文范围；未提取到值保持空值并记录原因。明确“0”、明确“不允许”、材料未提供以及执行失败分别保留。

第一版不做单位换算、跨文档实体合并或自动权威评级；这些需要新的模型任务和测试。代码仅校验结构与逐字绑定。校验失败记录为失败，不能静默纠正模型输出。

### 关系分子

从少量已绑定的原子记录开始，每次限定一个属性和一组待核对条件。关系判断引用输入原子 ID 与支持该关系的原文；不能只保留一个获胜值而丢弃其他来源。候选配对是召回步骤，不代表关系已成立；数值不相等也不自动证明冲突。

新来源进入后，根据依赖关系重新计算受影响节点，并留下新版本。没有被检查的候选和未完成的关系进入 coverage，不能把预算耗尽解释成没有冲突。

### 阶梯式总结

每个节点只接收本层选中的证据与必要关系，保留可追溯的下游 ID。单属性总结先交代共同条件、差异、未解决冲突与缺证据，再生成跨属性回答。高层总结不能把低层的“不确定”改成确定事实。

每层预先设定输入 token、输出 token、调用次数与时间预算；无界回看和递归自我比较不进入设计。是否需要一次追加检索由模型给出明确缺项，执行器按剩余预算运行独立调用并记录。尚未冻结具体上层预算，不沿用 Reader 的 32-token 上限作为总结预算。

## 每层的验收问题

- 原子层：字段及否定是否准确？表头与行能否关联？所有字段引用是否能打开同一历史原文？
- 分子层：不同条件是否被误报为冲突？明确更正是否有来源证据？输入换序后关系是否稳定？
- 总结层：是否遗漏不利或冲突证据？是否把缺证据写成不存在？引用能否沿依赖回到准确原文？
- 运行层：是否完成、是否超预算、哪些来源未检查、失败是否被如实展示？

回答质量和运行性能分别报告。模型或 State 可以替换，但每次替换必须通过同一契约的回归与新材料测试。当前不以模型升级、采样变化或服务启动成功代替语义验收。
