# G1j 2.9B / 7.2B 固定材料对照测试

## 结论

7.2B 是值得继续验证的主模型候选，但当前不能直接替换生产。它在本轮固定材料直接回答中减少了重复生成，事实与完整性优于两组 2.9B；引用、缺证据处理、修订关系和属性对齐仍有明显问题。

原子化方向得到局部支持：人工筛出的短逐字证据消除了一个 2.9B 长材料换序后的循环。但“整份来源 → 一次生成全部原子 JSON”的实验失败，7.2B 在提取长重复材料时仍会展开无关条目直至输出上限。必须先限定证据范围和单次任务粒度，再做原子提取。

没有修改 `llamaindex-retrieval/src/` 或 `web/`，没有训练，没有切换生产模型，也没有改动业务索引。

## 实验设计和边界

主计划在运行前冻结，见 `llamaindex-retrieval/eval/g1j72-20260920/PLAN.json`。同一官方 RWKV CUDA 运行时、BF16 权重、argmax、EOS token 0、G1j no-think 协议。Writer 输出上限 2,048 token；提取 512；关系判断 256。不自动重试，不改写模型输出。

材料共 28 题：8 道已有对比题、8 道普通问答回归、12 道控制实验。控制实验覆盖单一来源、一致来源、同范围冲突、来源换序、不同模式、明确撤回、预约与交付、缺证据、长重复材料和单位不可比。

这是合成材料及已暴露回归题的开发评测，不是盲测。Writer 输入使用统一的固定材料表示，2.9B tuned 组是生产 Writer State 的参考组，不等于实际生产检索流水线回放。各模型可能共享 GPU 并发运行，因此不以耗时宣称吞吐提升。

全部 9 组运行完成，共 **156 个案例执行、159 次模型调用**。159 次客户端原始输出与原生 token 回执逐一匹配，包含所有失败和截断。见 `artifacts/g1j72-20260920/EXECUTION-SUMMARY.json` 和 `raw-traces.tar.gz`。

## 直接回答：模型升级改善收敛，引用没有同步解决

| 模型与 State | 正常 EOS | 事实与完整性通过 | 严格通过：事实、完整性、引用及正常结束 | 输出 token，含 EOS |
| --- | ---: | ---: | ---: | ---: |
| 2.9B，零 State | 25/28 | 22/28 | 16/28 | 7,775 |
| 2.9B，现用 Writer State 300 | 28/28 | 20/28 | 14/28 | 1,273 |
| 7.2B，零 State | 28/28 | 26/28 | 16/28 | 1,717 |

逐题事实和引用为助手人工复核，不是独立专家复核。严格引用评分要求有效、可点击的 `[资料 N]`，每项事实与派生比较结论有对应支持；非法合并标签、未知编号、漏引和错引均失败。多个合法标签可以共同支持一个复合结论。缺证据拒答本身允许无引用。详见 `MANUAL-REVIEW.json`，勿把“正常 EOS”当作答对。

### 关键失败

1. **2.9B 短材料也会循环。** `comparison_smoke_006` 只有两份很短的材料，一份为已废止的99 W草案，一份为核准16 W/21 W。零 State 先给出两个值，然后反复输出“99 W已废止”，直到2,048 token。
2. **来源顺序能影响收敛。** `controlled_long_conflict` 保留18 W/25 W并结束；颠倒两份长来源后的 `controlled_long_conflict_reversed` 重复25 W并生成资料3至资料97等不存在的编号，直到上限。
3. **现用 State 能更快结束，却可能隐藏冲突。** 短冲突题只选择第二来源；换序后答案随之改变。另有核准功率、冷却方式和量产状态漏答。不能以较少输出 token 认定质量更高。
4. **7.2B 仍会无证据编造。** 无资料的桌面版/服务器版对比编造199元/299元及离线能力。另一个无资料题虽然说无法确定，仍引用不存在的资料2。
5. **长文内部编号被混为引用号。** 复位时间和校验码题只有一份来源；2.9B 引用了资料27，7.2B 引用了资料271。7.2B 还混入其他记录的否定说明。
6. **引用绑定仍然不可靠。** 7.2B 部分回答事实正确却不标引用，或用单方资料支持双方属性。更大模型没有消除这类错误。

## 原子化诊断

### 自动提取 → 关系判断 → Writer 的 v1 实验

| 模型 | 完成整条实验链 | 观察 |
| --- | ---: | --- |
| 2.9B，零 State | 0/12 | 原子或关系输出未通过冻结的数据契约 |
| 7.2B，零 State | 0/12 | 9题返回顶层数组而非要求的对象；3道长材料在首次提取时耗尽512 token |

这些失败不能都算成语义错误。顶层数组中部分内容可读，但不符合本次协议；校验器对其中一些输出记录 `TypeError: unhashable type: 'dict'`，原因是它按对象检查而模型返回了数组。该错误分类不够友好，但输出未被接受或修补，原始内容完整保留。

真正的语义问题同样存在：7.2B 把“不规定额定功率”的维护记录提取成带有18 W的主张。这种错误即使 quote 逐字存在，也不能通过“文本确实在原文中”这一检查证明其值受到支持。

因此，不能以这版失败断言所有分层架构无效，也不能把格式包裹修好就宣称原子正确。**短窗口选择、主张提取、字段与原文支持关系需要分别验收。**

### 人工短引文 → 同一 Writer

只改变逐字证据范围，保持问题、Writer 提示与输出预算不变。人工引文为诊断用输入，不是已实现的自动提取能力。

| 模型 | 正常结束 | 事实与完整性 | 严格通过 |
| --- | ---: | ---: | ---: |
| 2.9B，零 State | 12/12 | 11/12 | 10/12 |
| 7.2B，零 State | 12/12 | 12/12 | 9/12 |

原先导致2.9B循环的长材料换序题，在短引文条件下能够保留25 W与18 W，并正确引用两个来源。2.9B仍把标准/增强模式误判为同条件冲突；7.2B仍有引用缺失和合并标签问题。短引文支持降低上下文干扰，但并未解决全部语义和引用问题。

## 独立关系判断

在 v1 提取契约失败后增加一个明确标记的诊断扩展：`PLAN-relations.json`。输入人工选择的短逐字证据，沿用相同关系提示和256 token上限，隔离提取误差。没有把期望关系提供给模型，没有训练；材料已暴露，不是新盲测。

| 模型 | 结构及正常结束 | 关系类别正确 |
| --- | ---: | ---: |
| 2.9B，零 State | 12/12 | 7/12 |
| 7.2B，零 State | 12/12 | 9/12 |

7.2B的三个类别错误：不同模式归为 supported 而非范围差异；明确撤回旧值仍判为冲突；预约80台与交付0台误判为同一属性冲突。2.9B还错判了缺证据和单位不可比。理由与来源已逐项复核，JSON正确并不等于语义正确。

## 对架构的修改结论

1. **先减少进入原子提取器的内容。** 在现有 Reader 窗口选择之后继续定位短证据跨度，携带必要父级上下文；不能直接对整份长记录生成原子清单。
2. **原子输出采用最小必要协议。** 先验证一个来源、一个所求属性及原文位置，再扩充条件字段；评估索引/跨度选择是否比自由复制整句更稳定。不得由程序编造或修正语义字段。
3. **把问题覆盖状态与证据关系分开。** “能回答”与“两个主张同范围”不是同一个分类维度。顺序验证对象/属性、条件/时间范围、显式修订，再判断是否存在未解决矛盾。
4. **分子持久保存双方证据。** 引用和冲突关系绑定不可变原子ID及来源版本。一次 Writer 或 Reviewer 输出不得删除反对证据。
5. **最终表达不重新汇总全部长文。** 先输出每个属性的结论卡，再形成对象/主题小结；每次只输入当前小节需要的逐字证据和有边界的关系记录。
6. **引用标识与文档编号分离。** 前端用已有数据中的主张—证据映射渲染卡片引用；自然语言结论仍须模型明确绑定证据并通过检查。原始回答引用错误时记录失败，不能在后处理中替换原始回答的编号。
7. **先定协议和评测，再训练7.2B各角色。** 当前结果不足以默认启用7.2B。下一阶段优先做短证据选择和属性/范围对齐，验收后接入分子、阶梯总结及Wiki。原2.9B State不得直接迁移。

详细数据模型、依赖失效、版本发布和文件改动边界见 [架构设计提案](g1j72-evidence-architecture-20260920.md)。
